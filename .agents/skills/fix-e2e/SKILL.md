# Fix end-to-end failures

Use this skill when asked to run `yarn test:e2e` and resolve any failures or flakes in Argus.

1. Read the relevant `!notes/` indexes and task notes, inspect `git status`, `package.json`, and `playwright.config.ts`, and preserve existing work. Check for a running suite and existing test servers before starting. If an Argus dev server from this checkout occupies the test ports or uses the personal config, stop it with `yarn dev:stop` without asking the user, verify the ports are free, and let Playwright start its server with the test config. Confirm that every listener on ports 5173 and 3001 belongs to this checkout before using `yarn dev:stop`, since that command kills both listeners. Never launch a duplicate or stop a server that belongs to another task; if ownership is uncertain, report the blocker. Establish which skips are intentional.
2. Run `yarn test:e2e` and monitor it through the final Playwright summary. Give progress updates at least every 60 seconds. If one infrastructure or setup failure is cascading across the suite, capture representative evidence and stop the run rather than spending the remaining tests on the same failure. Count every full-suite invocation as one attempt, including an interrupted run. Playwright's built-in per-test retry is part of that invocation. **Never exceed three full-suite attempts in one invocation of this skill.** Focused test runs, builds, and diagnostic probes do not consume this limit.
3. **After every attempt with a `failed` or `flaky` test, find the causal path before another full-suite run or a final report.** A retry that passes is still a flake. Preserve the first error and retry result, screenshot or trace when available, and surrounding server output before a focused run can replace test artifacts. Trace the failing assertion through the test setup, UI or protocol, backend, and provider as relevant. State which behavior broke, why it broke, and what evidence rules out competing explanations. Distinguish a product defect, incorrect test expectation or fixture, environment problem, and timing/resource contention with evidence. Reproduce each distinct failure with a focused run or probe where possible; group failures only after confirming a shared cause. For an environment failure, repair the environment and rerun the same focused reproduction. Do not treat a process restart or a passing retry alone as proof that the underlying issue is fixed.
4. Fix the product behavior at the layer that caused the failure. If the test is wrong, show the intended behavior and the exact flaw in its expectation, setup, cleanup, or synchronization before editing it. A green result alone is not evidence that the code is correct. Do not skip, weaken, or inflate timeouts to conceal a product defect or an unknown cause. Keep assertions meaningful. Add or adjust a regression check that would fail for the original cause, then verify the behavior with focused tests or a direct probe. Follow the repo's coding and test-data rules; do not reformat unrelated code.
5. Only after the failures from the previous attempt have a supported cause, a fix at that cause, and focused verification, run the full suite again if attempts remain. Success requires both explained and verified fixes and a completed run with zero failed and zero flaky tests; intentional skips are acceptable. After the third attempt, continue diagnosis, fixes, and focused verification without another full-suite run. Report each failure's cause, code or test change, and verification. If a cause remains unknown, say so even if a retry or later run is green. State that the full suite is not verified clean when failures remain. Do not claim success from a focused run or a Playwright retry.

Do not commit, push, deploy, or publish results unless separately requested.
