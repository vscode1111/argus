# Argus - VS Code Extension

AI coding assistant powered by Claude, built as a VS Code extension.

## Project Structure

```
src/
  backend/
    index.ts            - WebSocket server setup, ping/pong, Origin validation, nonce auth, upgrade handler, optional idle self-shutdown (idleTimeoutMs/onIdleShutdown)
    daemon.ts           - Always-on daemon entry: fixed port (3017), 10-min idle-exit, writes/cleans discovery file, single-instance guard (compiled to out/backend/daemon.js)
    daemonInfo.ts       - Discovery-file helpers shared by daemon and extension (~/.claude/argus-daemon.json: read/write/clear, isProcessAlive, DEFAULT_DAEMON_PORT)
    channel.ts          - Multi-session channel registry: Map<workspaceDir, ChannelData>; one ChannelData per unique ?dir= holding a Map<key, SessionEntry>; each SessionEntry has its own SessionState, clients Set, browsingClients Set, history (ChannelMessage[], MAX 200), streaming snapshot, and lastActivityAt; createBroadcastForEntry() scopes broadcast to entry clients (SESSION_STREAM_EVENTS gated for browsingClients); getOrCreateChannel() returns a Channel facade: addClient(ws, fresh?, sessionId?) (joins defaultEntry = most recently active, an isolated new entry when fresh, or live-attaches to the entry bound to sessionId - deep link, overrides fresh, returns true on such an attach), removeClient (30s grace timer, then killProc on eviction), getClientState (per-client routing via clientEntry Map), moveToNewSession (fresh entry for one client, old entry keeps running), setBrowsing(ws, browsing, sessionId?) (records the browsed id in ChannelData.clientViewing - the entry keeps pointing at the streaming session, so this is the only record of what the client actually has on screen), getViewingSessionId(ws) (that browsed id, for handlers that must read the transcript the client is actually looking at), detachToBrowsedSession(ws) (moves a browsing client into its own entry bound to that id and returns its state; undefined when not browsing), attachToLiveSession(ws, sessionId) (joins the entry mid-turn on that session, replaying its history + snapshot; undefined when no OTHER entry is streaming it), replaySnapshot, replayHistory (entry history + snapshot, deep-link initial sync); module-level broadcastToAllChannels(msg) sends to every client across ALL workspace channels (config-global settings changes); listActiveSessions() reports every entry currently mid-turn (state.sessionId set, currentProc live, cliDone false) as {id, workspacePath, startedAt} and notifyActiveSessions() pushes that set to all clients, coalesced on a timer and skipped when unchanged (triggered from the entry broadcast on thinking_start/done/error/sessionId/clear and from entry eviction); applyMsg() mirrors webview reducer to rebuild each entry's history; destroyChannel() for tests
    session.ts          - Per-client handler (attachClientHandlers); resolves s = channel.getClientState(ws) on each message for correct per-client routing; first-client init block (guarded by !s.sendLog) sets up watchdog/staleTimer/emitSyntheticSend/flushAskFollowUp; newSession calls channel.moveToNewSession() (isolated entry for this client only, old entry and its proc keep running); switchModel/switchEffort/switchThinking write argus.json and notify via broadcastToAllChannels() (model/effort/thinking are config-global; getInfo and CLI spawns re-derive them from readConfig() at use time, nothing cached per entry); broadcast events sent via s.broadcast() (entry-scoped), per-client responses sent via ws.send()
    sessionState.ts     - SessionState interface and createSessionState factory (shared mutable state; broadcast assigned by channel.ts)
    cliHandler.ts       - CLI stdout event parsing (handleCliEvent), proc lifecycle (attachProcHandlers)
    watchdog.ts         - Timeout detection, auto-retry scheduling (createWatchdog)
    login.ts            - OAuth login flow orchestration (createLoginHandler)
    filePreview.ts      - Shared file preview reader (path validation, image detection, used by both backend and extension)
    toolResult.ts       - Flattening of CLI tool results with the base64 images taken out: stringifyToolResult(content) turns a string / block array / single block into the string the webview renders, replacing an image block with `[image image/jpeg 174 KB]` (imageMarker); imageFromBlock() is the shared "is this a base64 image" test, used here and by sessions.readToolImage
    cli.ts              - Claude CLI spawn helpers, process kill, allowed tools list
    config.ts           - ArgusConfig type, readConfig/writeConfig (mtime-based cache), DEFAULT_CONFIG
    workspaceInfo.ts    - buildWorkspaceInfo(path, version, fallbackModel?): single builder of the workspaceInfo reply to getInfo - model/effort/thinking read fresh from argus.json, optional fallbackModel (serverDefaultModel on the server path); shared by session.ts and ChatPanel's VS_ONLY getInfo path so the two replies cannot drift
    version.ts          - readServerVersion(): version of the build this server process runs from (package.json above the compiled output); used by the daemon discovery file and the serverInfo "Server" row
    skills.ts           - Slash command and skill discovery (readCommandsDir, readSkillsDir)
    accountUsage.ts     - fetchAccountInfo (claude auth status --json), fetchUsage (live /api/oauth/usage via OAuth token; parses the `limits` array first - only source of model-scoped windows like "Weekly Fable", carried as RateLimitInfo.label - legacy known-window keys as fallback), parseRateLimitEvent (stream fallback), fetchModels (live /v1/models, 5-min cache; keeps `max_input_tokens` as ModelInfo.contextWindow)
    usageInsights.ts    - Local usage insights ("What's contributing to your limits usage?"): collectUsageInsights(force) scans ~/.claude/projects transcripts (7-day mtime prefilter, per-session subagents/ included, substring extraction without JSON.parse, requestId dedup) and mirrors the official CLI's algorithm - cost = (cache_read + input*10 + cache_creation*12.5 + output*50) * family tier (fable 10 / opus 5 / sonnet+unknown 3 / haiku 1); behaviors cache_miss (>100k uncached input), long_context (>150k context), subagent_heavy (>=3 isSidechain events or >50% subagent cost per session), high_parallel (4+ distinct sessions per 5-min bucket), cron (8+ distinct active hours); attribution tables from the CLI's attribution{Skill,Agent,Plugin,McpServer} fields; day+week reports in one pass, 60s cache + shared in-flight promise
    usagePoller.ts      - One usage-limit poller per server process, never per client: startUsagePoller (called from startServer once it is listening, so the daemon and the dev server both poll; ARGUS_USAGE_POLL=0 kill switch, set for e2e daemons and the Playwright webServer), noteUsageActivity (any send / forced refresh - resumes a paused poller with an immediate fetch), getUsageSnapshot (last good windows + fetchedAt, kept on a failed poll), stopUsagePoller, and the pure usagePollActive(lastActivityAt, now) gate over USAGE_POLL_INTERVAL_MS (60s) / USAGE_ACTIVE_WINDOW_MS (1h); a successful poll broadcasts `usageLimits` to every client of every channel, skipped when the window set is unchanged
    modelData.ts        - Model metadata upkeep: modelFamily/describeModel (family-based descriptions, fable/opus/sonnet/haiku, mirrors the CLI's substring classifier), contextWindowFor (per-model context window from the cached /v1/models list, snapshot-date tolerant, DEFAULT_CONTEXT_WINDOW 200k when unknown - the window is NOT family-derivable, opus-4-5 is 200k while opus-4-6 is 1M), extractFamilyDescriptions (scans the installed CLI bundle for the picker wording), detectDefaultModel (minimal CLI turn in tmpdir), refreshModelData (writes runtimeDefaultModel + modelFamilyDescriptions + modelListCache via the pure applyRefreshResult, which advances modelDataAttemptedAt always but modelDataUpdatedAt only when a model list actually came back), shouldRefreshModelData (pure two-clock gate: success older than 24h AND last attempt older than 1h), scheduleModelDataRefresh (daemon startup hook: stamps daemonLastStartAt, then defers to shouldRefreshModelData, hourly re-check, ARGUS_MODEL_REFRESH=0 kill switch)
    sessions.ts         - Local session history: listSessions/loadSession/deleteSession over CLI transcripts in ~/.claude/projects/<encoded-cwd>/*.jsonl (dir path-encoding, replay parser, traversal guards); readToolImage(sessionId, workspaceDir, toolUseId) reads one tool call's image back out of the transcript (cheap `line.includes(id)` prefilter before JSON.parse, id regex-validated, same resolveSessionFile guards) so a preview can show what the model saw after the file itself is gone
  frontend/
    extension.ts        - Activation entry point, starts WS server on dynamic port, registers commands/providers
    chat/
      ChatPanel.ts      - WebviewPanel lifecycle, VS Code-specific message handlers, injects WS URL into HTML
      ChatMessage.ts    - Message types
    providers/
      InlineSuggestProvider.ts  - Inline completions (Copilot-style)
      CodeLensProvider.ts       - "Ask Argus" code lens
    utils/
      config.ts         - Extension settings helpers
      workspace.ts      - VS Code workspace helpers
      win32Focus.ts     - Win32 FFI (koffi) for reliable window focus on notification click; uses SwitchToThisWindow (crosses virtual desktops) then the SetForegroundWindow/AttachThreadInput dance
      win32Clipboard.ts - Win32 FFI (koffi + GDI+) for copying images to system clipboard (CF_DIB + PNG)
      win32Toast.ts     - Real Windows OS toast (Action Center) fully in-process via koffi FFI driving the WinRT ToastNotification COM API directly (no subprocess); registers an AppUserModelId under HKCU (RegSetKeyValueW) with `DisplayName` (shows as "Argus") plus a stub `CustomActivator` CLSID (no backing COM server - required so protocol-activation toasts stay clickable from the Action Center); title/body XML-escaped; optional `launchUri` adds `activationType='protocol' launch='<uri>'` so clicking the toast ShellExecutes the URI (click-to-focus, no COM activator / no cross-thread callback); ~14ms cold / ~4ms warm; returns false on failure so the caller can fall back
cmd/
  start-argus.bat       - Launch dev server (double-click from Explorer)
  start-argus-daemon.bat - Launch the always-on daemon windowless/detached (via scripts/daemon.vbs); self-exits when idle
  stop-argus-daemon.bat - Stop the running daemon (via scripts/daemon-stop.js: reads pid from the discovery file, kills it, clears the file)
  ctx-install.bat       - Install context menu entry (run as admin)

  kill-claude.bat       - Kill all running Claude Code processes
server/

  tsconfig.json         - TypeScript config for server
scripts/

  dev-stop.js           - Kill running dev processes
  context-menu.js       - Cross-platform context menu install/uninstall (Windows registry / Linux .desktop entry)
  launch.js             - Opens Chrome in app mode with optional ?dir= param (cross-platform Chrome paths)
  launch.vbs            - Windows-only VBS wrapper for windowless launch (invoked by context menu registry)
  daemon.vbs            - Windows-only VBS wrapper that launches out/backend/daemon.js windowless/detached (invoked by start-argus-daemon.bat)
  daemon-stop.js        - Stop the running daemon: reads pid from ~/.claude/argus-daemon.json, kills it, clears the file (idempotent; cross-platform)
  update-model-data.js  - Manual model-data refresh (`yarn update-models`): thin wrapper over compiled out/backend/modelData.js refreshModelData() - detects the CLI default model, extracts family descriptions from the CLI bundle, caches /v1/models; the daemon runs the same refresh automatically once a day
  test-clean.js         - Kill leftover e2e-run processes (orphaned `claude --print` agent CLIs, stale Vite/dev servers, Playwright runners + chromium, stray test daemons). Protects this session's whole ancestor chain and the real daemon's (discovery-file pid) entire process subtree - live user sessions are `claude --print` children of the daemon (via cmd.exe on Windows), so exact-pid protection alone used to kill mid-turn conversations; the subtree walk is NOT applied to the ancestor chain (it includes VS Code, whose descendants are the stale test processes this script exists to kill); never touches the user's normal browser. Flags: `--dry` (list only), `--no-claude`. The `yarn test:clean` script chains `dev-stop.js` after it (`node scripts/test-clean.js && node scripts/dev-stop.js`) for the reliable port-based dev-server kill.
  install-browsers.js   - Wrapper around `playwright install chromium` (pins to the project's @playwright/test version)
  install-browsers-manual.js - Windows-only manual browser installer that sidesteps the `playwright install` extraction deadlock (curl download + PowerShell Expand-Archive + INSTALLATION_COMPLETE marker, version-robust via the Playwright registry); see .claude/researches/playwright-install-hang.md
```

## Key Conventions

- Model: agent model is free-text (`argus.model`); empty/unset defers to the Claude CLI default. Inline completions default to `claude-haiku-4-5` (fast/cheap tier required)
- Streaming: always use `client.messages.stream()` + `finalMessage()`
- Tool approval: destructive tools (write_file, bash) require user confirmation via `showWarningMessage`
- No Python scripts - use Node.js/TypeScript for any tooling
- Webview UI is React 18 + TypeScript + Vite (lib/IIFE mode). Build with `yarn build`
- Webview styling uses CSS Modules (co-located `.module.css` files) with VS Code CSS variables (`var(--vscode-*)`) - no Tailwind, auto-adapts to any theme
- CSS Modules: camelCase class names for dot access (`styles.toolCall`), conditional classes via `.filter(Boolean).join(' ')`, shared modules in `components/shared/`, `composes:` for reuse
- CSS color tokens: diff/semantic colors defined as CSS variables in `global.css` (`--diff-added`, `--diff-removed`, `--user-msg-bg`, etc.) - never hardcode color literals in component CSS. **The unfilled part of any progress bar uses `--track-bg`, never `--input-bg`**: `--input-bg` is `--vscode-input-background`, which in some themes (Dark 2026, the one in `webview/index.html`) resolves to the *exact same colour* as the surface behind it, so the track disappeared and a 14% bar read as a floating stub with no sense of the full width. `--track-bg` is a `color-mix` wash of `--fg`, which contrasts by construction on any theme. Equal-colour bugs survive every layout assertion, so `e2e/usage-indicator.spec.ts` compares the computed track colour against its surface (verified red by reverting the token)
- Webview markdown rendered via `react-markdown` in `utils/markdown.tsx`
- Webview message protocol (extension -> webview): typed as `WebviewMessage` union in `ChatPanel.ts` - `thinking_start | thinking_chunk | text_chunk | tool_start | tool_end | done | error | message | clear | prefill | skills | workspaceInfo | log | clearLogs | loginUrl | loginResult | contextUsage | token_update | filePreview | retry_status | retry_clean | copyImageResult | user_inject | accountUsage | sessionList | sessionLoaded | workspaceList | allSessionList | dirList | clientCount | serverInfo | daemonRestarting | daemonStopping | sessionId | killAllClaudeResult | usageInsights | activeSessions | usageLimits | toolImage`
- Webview message protocol (webview -> extension): `send | stop | forceError | newSession | openFile | openUrl | getInfo | getSkills | retry | toolAnswer | login | loginCode | focusPanel | readFilePreview | copyImage | getAccountUsage | listSessions | resumeSession | deleteSession | renameSession | listWorkspaces | listAllSessions | switchWorkspace | listDir | getClientCount | getServerInfo | restartDaemon | stopDaemon | killAllClaude | getUsageInsights | getActiveSessions | getUsageLimits | readToolImage`
- Modal Escape handling: use `useEscapeKey(onClose)` hook from `hooks/useEscapeKey.ts` - do not duplicate keydown listeners
- Dialog state persistence: each centered modal (Session History, Workspace History, Account & Usage, Settings) remembers its **position, size, and selected tab**, persisted to `localStorage` so it survives a full page refresh. Backed by `utils/dialogState.ts` (a single `localStorage` key `argus.dialogState` holding a `Record<key, {pos,size,tab}>`, read/written per call via `getDialogState`/`patchDialogState`; storage errors are swallowed so geometry is best-effort). `clearDialogState()` removes that key (used by the Settings "Reset layout" button). Position/size are wired through `hooks/useDialogGeometry.ts` (replaces the old `useDraggable`): pass a `persistKey` (`Modal` forwards it; `SettingsModal` calls the hook directly). The hook applies width/height **imperatively** on the element (not via React's controlled `style`, which only carries the drag position) so the native CSS `resize: both` grabber keeps working; size is recorded **only** when the user actually drags that grabber (a `pointerdown` landing in the bottom-right ~18px zone, committed on `pointerup`), never on content-driven size changes - so a content-height modal (e.g. Settings) does not silently persist a size the user never set just from switching tabs; drag end records position. On mount, size is restored from the store or falls back to `defaultWidth`/`fullHeight`. The hook also returns `reset()`, which clears the live element's inline width/height and recenters it (`setPos(null)`) so a "Reset layout" click snaps the open modal back without a reopen. Tab persistence lives in each modal: `tab` initializes from `getDialogState(key)?.tab` and a `setTab` wrapper calls `patchDialogState`; Session/Workspace re-trigger their lazy tab loads (`listAllSessions` / `browseTo`) on mount when the restored tab is the lazy one. SettingsModal keeps its **tab** in `localStorage` (`argus.settingsTab`) and only adds geometry to the store. SettingsModal's footer has a bottom-right **"Reset layout"** button (`.resetCorner`, mirrors the bottom-left `dev` button) that calls `clearDialogState()`, removes `argus.settingsTab`, and `drag.reset()`s the open modal, then flashes "Layout reset" for 1.5s. e2e: `e2e/dialog-state.spec.ts` (mock, incl. persist-across-refresh + Reset layout) and `e2e/dialog-state-integration.spec.ts` (integration)
- Modal portals: FileViewerModal, DiffViewerModal, and ImageViewerModal use `createPortal(jsx, document.body)` to render outside the React tree, avoiding z-index stacking issues when modals are opened from inside the scrollable MessageList during streaming
- Preview ownership (file / diff / image): the **open state must not live in the component that was clicked**. A tool block is rendered by `StreamingMessage` while its turn runs and by `ChatMessage` once the turn commits, so the clicked `ToolCall` is unmounted the instant the turn finishes - which closed the modal under the user's cursor mid-read (the portal only fixes stacking, not lifetime; a `FilePathLink` inside streaming markdown had the same problem, plus constant re-rendering). `webview/src/contexts/PreviewContext.tsx` hoists it: `PreviewProvider` sits **above** `AppInner` in `App.tsx` and owns a stack of `PreviewRequest`s - `{kind:'file', path, content, line?, copyText?}`, `{kind:'diff', path, oldString, newString}`, `{kind:'path', path, line?}` for "content not in hand", or `{kind:'toolImage', path, toolUseId}` for an image a tool returned. Consumers call `usePreview().open(req)`; nothing renders a preview modal itself except `AutoFileViewer` (the `?file=` launch param, already App-level). A `path` request is resolved by the host - it posts `readFilePreview`, matches the `filePreview` reply by exact path or `endsWith` (the backend answers with a resolved absolute path) and only then pushes the frame, so no empty modal flashes; this replaced two near-identical copies of that fetch in `ToolCall` (images) and `FilePathLink`. The state is a **stack**, not a slot, because previewed markdown linkifies paths too, so a path clicked inside a preview opens on top instead of replacing it; `onClose` at depth i truncates to i. `refresh(req)` replaces an open entry matched by `key` (`<toolCallId>:file` / `:diff`) and returns the **same array reference** when nothing matches, so the per-ToolCall effect that keeps a background Bash task's late output in sync doesn't re-render the provider on every result. Because `children` is a stable element, provider state changes never re-render the message list. The same rule applies to any state that must outlive a turn, not just previews: [!notes/common/state-lifetime-in-message-tree.md](!notes/common/state-lifetime-in-message-tree.md); e2e: `e2e/modal-persistence.spec.ts`
- **A tool's images never travel inside its result.** A Read of an image comes back as a base64 block, and those blocks were by far the largest thing Argus put on the wire: one real session held 48 of them, **23.4MB inside a 24.2MB `sessionLoaded` payload**, re-sent on every replay and reconnect (`ws` 8.20.0 defaults `perMessageDeflate` to false and `src/backend/index.ts` passes no override, so it crosses raw; base64 of JPEG barely deflates anyway). None of it was ever rendered - the preview re-read the file off disk, so an image the agent had since renamed, packaged or deleted opened as `Error reading file: ENOENT` while the bytes the model actually saw sat in the transcript. `stringifyToolResult()` (`src/backend/toolResult.ts`) therefore replaces every image block with `[image image/jpeg 174 KB]` on **both** paths that feed the webview - live (`cliHandler`'s `handleUserEvent` and `handleToolResult`) and replay (`sessions.loadSession`) - and the bytes are fetched one at a time, per click: `ToolCall` opens `{kind:'toolImage', toolUseId}`, `PreviewContext` posts `readToolImage {toolUseId, path}` and matches the `toolImage` reply **on the call id** (exact - the path-suffix match `filePreview` needs cannot tell two images in one turn apart), and `session.ts` answers from `readToolImage(channel.getViewingSessionId(ws) ?? s.sessionId, ...)`, the browsed session winning because that is the transcript on screen. It falls back to `readFilePreview(path)` only when the transcript has no image for that call (an old session, or a result line the CLI has not flushed yet), so the disk is the exception rather than the source. Measured on the reported session: **24.2MB -> 0.8MB**. Because the bytes now arrive per click rather than with the message, a content-less request (`path` **or** `toolImage`) **opens its modal immediately** and fills it in when the host answers: `open()` pushes a `Frame` with `loading: true` and a unique `loadId`, and the reply is written into *that* frame by id (`settle()`), so a second preview opened while the first is in flight cannot be overwritten by it. `FileViewerModal` takes a `loading` prop and renders `.loadingBody` + `.previewSpinner` (`data-testid="preview-loading"`) in place of the body, hiding the encoding select while there is nothing to decode; the header already shows the path, so the window says what it is fetching. Deferring the open until the content arrived (the first shape of this) left the click looking ignored for a second or more over a remote link. `PREVIEW_TIMEOUT_MS` (20s) closes the loop: the host answers even when the read failed (the error arrives as the content), so silence means a lost message or reply, and the frame settles to a "connection may have dropped" message rather than spinning forever. Same rule for anything large a tool can hand back: [!notes/common/large-tool-payloads.md](!notes/common/large-tool-payloads.md); e2e: `e2e/tool-image-preview.spec.ts` (mock) and `e2e/tool-image-preview-integration.spec.ts` (real CLI, the file deleted before the click)
- Errors use `showError()` helper in ChatPanel - shows VS Code error notification with "View Output" action
- AgentSession and ChatPanel use a shared `vscode.OutputChannel` ("Argus") for stderr and error logging
- Image paste: clipboard images are base64-encoded in the webview, sent via `--input-format stream-json` NDJSON to the Claude CLI with `type: "image"` content blocks

Delivery is environment-routed in `App.tsx` via `fireNotification(title, body)`: in the **browser** dev/app window (`location.protocol !== 'vscode-webview:'`) it uses the web `Notification` API directly (clicking focuses the window; requires `Notification.permission === 'granted'`, requested on first enable); in the **VS Code** webview (`vscode-webview:` protocol) the web Notification API cannot reach the OS, so it posts a `notify {title, body}` message (added to `VS_ONLY` in `chat.html`) that `ChatPanel.ts` turns into a notification: on **Windows** it fires a real OS toast via `showWindowsToast(title, body, log, focusUri)` (`win32Toast.ts`, in-process koffi FFI -> WinRT, shows in the Action Center even when VS Code isn't focused), where `focusUri` is `vscode://<getExtensionId()>/focus`; clicking the toast uses **protocol activation** (the toast XML carries `activationType='protocol' launch='<focusUri>'`), so the shell ShellExecutes the URI, VS Code comes to the foreground, and the `UriHandler` registered in `extension.ts` (`uri.path === '/focus'`) calls `ChatPanel.revealForActivation()` to focus the last-focused panel - this avoids a COM activator and the cross-thread WinRT `add_Activated` callback that koffi can't safely service. If `showWindowsToast` returns false (non-win32 or FFI failure) it falls back to `vscode.window.showInformationMessage(...)` with an "Open" action that reveals/focuses the panel via the cached HWND (`win32Focus.ts`). The code-block markup is deliberately **two** elements and must stay that way: a non-scrolling `div.code-block-wrapper` (`position: relative`, `width: fit-content`, `max-width: 100%`) wrapping the `pre` that carries the background, padding and `overflow-x: auto`. - File-path regex pair and the `!notes` convention: two regexes run in sequence over the same text and must be widened together - `WIN_PATH_RE` (`markdown.tsx`) escapes backslashes **before** the markdown parser eats them, `FILE_PATH_RE` (`filePath.tsx`) linkifies the parsed text; a class one accepts and the other rejects yields a half-linked path. Both allow `!` in **directory** segments (the `!notes/` convention: `D:\_Projects\CCS\!notes\tasks\x.md`) but not in the final filename class, so prose like `done!file.md` is not swallowed. **The filename suffix is `\.\w+(?:-\w+)*`, not `\.\w+`**, because a dotfile is routinely hyphenated (`.corp-account`, `.menu-cms`) and `\w` excludes `-`: the match used to stop mid-name, and the two regexes then failed *differently* on the same path - in a code span `C:\…\credentials\.corp-account` linkified as `C:\…\credentials\.corp` (a file that does not exist, so the click opened ENOENT), while in prose `WIN_PATH_RE` missed it entirely and markdown ate the backslashes around each dot (`C:\Users\Admin.claude\…\credentials.corp-account`). `\w` also excludes Cyrillic, which keeps a Russian suffix ("`.md`-файл") out of the link. - Multi-session shared channels: clients connecting with the same `?dir=` join one `ChannelData` (keyed by workspace dir). `channel.ts` holds a `Map<workspaceDir, ChannelData>` registry. Each `ChannelData` contains a `Map<key, SessionEntry>` of concurrent sessions and a `Map<WebSocket, SessionEntry>` routing table. **SessionEntry** holds: `state: SessionState`, `clients: Set<WebSocket>`, `browsingClients: Set<WebSocket>` (clients viewing a different transcript via `resumeSession`), `history: ChannelMessage[]` (MAX 200), `snapshot` (in-progress streaming state for late-join replay), and `lastActivityAt`. Each entry has its own broadcast function (scoped to that entry's clients). **Session lifecycle**: new clients join the most recently active entry (`defaultEntry`); `newSession` calls `channel.moveToNewSession(ws)` which creates a fresh `SessionEntry` for just that client - the old entry and its CLI proc keep running (other clients continue to see the turn). When the last client leaves an entry, the watchdog is stopped and a 30s grace timer starts; the proc is NOT killed during the grace window (it runs on, broadcasts go to zero clients, and a returning client can rejoin). **When the timer actually evicts the entry, `scheduleEntryCleanup` calls `killProc(entry.state.currentProc)`**: an evicted entry is unreachable (no client can rejoin it), so without this its CLI process lingers for the life of the server. That leak was severe once `addClient(ws, fresh)` gave each browser client its own entry - every abandoned entry leaked a `claude` process until the OS refused new spawns (see `!notes/issues/integration-suite-cascade-crash.md`). **SESSION_STREAM_EVENTS gating**: `thinking_start`, `text_chunk`, `tool_start`, `tool_end`, `done`, `error`, `message`, `user_inject`, `token_update`, `retry_*`, `contextUsage` are suppressed for browsing clients (those in `entry.browsingClients`); control events (`clear`, `modelChanged`, `log`, etc.) always reach all clients. **Two-send-path rule**: broadcast events use `s.broadcast()` (entry-scoped, gated for browsing clients); per-client responses (`settings`, `skills`, `filePreview`, `accountUsage`, `sessionList`, `clientCount`, `serverInfo`, etc.) use `ws.send()` directly. `switchModel`/`switchEffort`/`switchThinking` are global settings: they use `channel.forEachSession()` to update all entries' states and `channel.broadcastToAll()` to reach every client across all entries. `index.ts` calls `getOrCreateChannel(workspaceDir)` then `attachClientHandlers(ws, channel, MODEL, hooks)`. First client on an entry triggers `initChannelSession` (sets `s.sendLog`, watchdog, `emitSyntheticSend`); later clients skip that block (`!s.sendLog` guard). e2e coverage in `e2e/shared-channel-integration.spec.ts` (broadcast, late-join replay, per-client isolation, isolated newSession, model broadcast, workspace isolation, Bug 1 no-kill-on-resume, Bug 2 browsing-client stream gating)
- Send while browsing another session: a send from a client that navigated away via `resumeSession` belongs to **the session it is looking at**, not to the turn still streaming in the entry it left. `handleSend` only ever receives the entry `SessionState`, never the `ws`, so it cannot tell a browsing client from a live one - left in place, its mid-turn-inject branch (`s.currentProc?.stdin?.writable && !s.cliDone`) fired purely because the *entry* had a live proc, and the text was written into the other session's stdin. The sender saw nothing back (`user_inject` and `message` are both in `SESSION_STREAM_EVENTS`, gated away from browsing clients) while every client watching that session got the stray prompt as an inject bubble. Fix: `handleResumeSession` records the browsed id via `setBrowsing(ws, true, id)` into `ChannelData.clientViewing` (the entry's own `sessionId` deliberately still points at the streaming session, to keep its `--resume` arg correct, so nothing else remembers what the user has on screen), and the `send` handler calls `channel.detachToBrowsedSession(ws)` **first** - moving the client into its own entry bound to that id (transferring `owner` exactly as `moveToNewSession` does, so a later reconnect rejoins the session the user is actually in). The new entry has no proc, so `handleSend` takes the normal spawn path with `--resume <browsed id>`, and the session left behind keeps streaming untouched. `clientViewing` is cleared on `setBrowsing(ws, false)`, `moveToNewSession`, `detachToBrowsedSession` and `removeClient`. e2e: `e2e/browse-send-routing-integration.spec.ts` (the browsed send starts a real turn and produces no `user_inject`; a second client watching the live session never receives it) - both raw-WS, because "browsing" only exists while a real CLI process is mid-turn
- Resuming a session that is streaming in another entry: `handleResumeSession` calls `channel.attachToLiveSession(ws, id)` **first**. Without it the handler only ever rebound the client's **own** entry's `sessionId` and replayed **that** entry's snapshot, so a session mid-turn in a different entry (a second panel, or - since the browse-send fix - the entry the client detached from) was served from `loadSession`: the transcript on disk stops at the last committed turn, so the client got a stale view with **no progress indicator and no further output**, while the turn ran on invisibly. `attachToLiveSession` scans for an entry whose state has that `sessionId` with a live `currentProc` and `cliDone === false`, skipping the client's current entry (already being there is an ordinary return-to-live resume, which the existing branch replays itself), and `joinEntry`s the client so it receives that entry's history + streaming snapshot. The handler then sends a `token_update` (the snapshot replay restores the blocks but not the counters behind the timer) and returns before the disk-load path. e2e: `e2e/resume-live-session-integration.spec.ts`
- Session deep link: a session is addressable by URL - `http://<host>:<port>/?session=<id>` (`?dir=` optional). At WS upgrade (`src/backend/index.ts`) the server resolves the id to its workspace via `findWorkspaceForSession(id)` in `sessions.ts` (scans `~/.claude/projects/*/<id>.jsonl` and recovers the transcript's recorded `cwd`; UUID-validated so a malformed id never reaches the filesystem) **before** `getOrCreateChannel` - the resolved workspace **wins** over `?dir=` (a dir copied between machines can be stale; the mismatch is logged, not fatal), and an unresolvable id is dropped so the connection falls back to `?dir=` alone. `channel.addClient(ws, fresh, sessionId)` live-attaches the socket to the entry currently bound to that sessionId (overrides `fresh`); when no live entry owns the id, the fresh entry gets `s.sessionId = id` (idle entries only) so the next send spawns with `--resume`. A brand-new chat has no id until the CLI assigns one, so `handleSystemEvent` (`cliHandler.ts`) broadcasts a `sessionId {id}` event on the `init` subtype when the id changes; both browser shims listen for it and `updateUrl()`, so a fresh conversation becomes shareable/reloadable without a click. `sessionId` is in `SESSION_STREAM_EVENTS` (a browsing client is viewing another transcript and must not have its address bar rewritten). Reload of a deep-linked **finished** session used to land on a blank page: the first load bound an entry to the id but filled it from disk, so the entry's in-memory history was empty and re-attaching replayed nothing. `channel.replayHistory()` now returns `false` when the entry has neither history nor a snapshot, and `session.ts` falls back to `loadSession` in that case. e2e tests in `e2e/session-deep-link-integration.spec.ts` (live attach + remote stop, no-dir workspace resolution + disk replay, new-chat id lands in the URL, reload of a finished deep link replays again, stale-dir override, malformed-id fallback)

- Single daemon server + connect-only extension: instead of one server per VS Code window on a dynamic port, a **single shared daemon** (`src/backend/daemon.ts` -> compiled `out/backend/daemon.js`) runs on a fixed port (default `3017`; precedence `ARGUS_DAEMON_PORT` env > `argus.json` `daemonPort` > 3017, resolved in `daemon.ts` via `readConfig()`; the discovery file records the actual port so the extension + browser adapt automatically - changing it needs a daemon restart) and is started **on demand** by the user (`cmd/start-argus-daemon.bat` via windowless `scripts/daemon.vbs`, or `yarn daemon` = `tsx src/backend/daemon.ts` for dev). It **self-exits after 10 min with zero connected clients** (idle is connection-count based, so an open panel mid-turn keeps its socket open and is never killed). Idle-shutdown is opt-in via `startServer`'s `idleTimeoutMs` + `onIdleShutdown` options (default off, so the dev path on 3001 never self-exits); `startServer` itself never calls `process.exit` - the daemon supplies `onIdleShutdown = () => process.exit(0)`. The idle timer is armed both at startup (so a daemon nobody ever connects to still exits) and on each last-client disconnect, and cleared on connect. Idle precedence: `ARGUS_DAEMON_IDLE_MS` env > `argus.json` `daemonIdleMs` > 10-min default (resolved in `daemon.ts` via `readConfig()`); `ARGUS_DAEMON_FILE` overrides the discovery-file path - the env vars are used by e2e to exercise idle-exit quickly against a throwaway file. Changing `daemonIdleMs` needs a daemon restart. Daemon behavior is covered by `e2e/daemon-lifecycle-integration.spec.ts` (discovery file, nonce gate, single-instance guard, idle self-exit + file cleanup) and `e2e/daemon-browser-integration.spec.ts` (the daemon-served browser UI mounts + connects, static allowlist), with shared spawn helpers in `e2e/daemonHelpers.ts`. The daemon writes a discovery file `~/.claude/argus-daemon.json` `{ port, nonce, pid, version, startedAt }` (mode 600), cleaned on idle-exit / SIGINT / SIGTERM / `process.on('exit')` (a hard kill leaves a stale file, handled below). Single-instance guard: on start it reads the file and exits early if that `pid` is alive (idempotent launcher); a crashed daemon's stale file has a dead pid so a fresh start proceeds. Discovery helpers live in `src/backend/daemonInfo.ts` (`DAEMON_FILE`, `DEFAULT_DAEMON_PORT`, `readDaemonInfo`/`writeDaemonInfo`/`clearDaemonInfo`, `isProcessAlive`). `clearDaemonInfo(onlyIfPid?)` is **ownership-aware**: with a pid it leaves the file alone unless that pid is the registered one, and `daemon.ts`'s `cleanup()` passes `process.pid`. Without this, a daemon that exits early (port already taken) wiped the live owner's registration and stranded the extension - it could neither connect (no file, and the nonce lives only in the owner's memory) nor respawn (port held). The `EADDRINUSE` message likewise distinguishes "pid N owns it (discovery file intact)" from an unreachable holder. **In-process self-restart** (for the browser-served "Apply" button, where there is no extension to respawn): `startServer`'s `onRespawn` option (supplied only by the daemon) + a `restartDaemon` WS message (`session.ts` -> `hooks.onRestartRequest` -> `doRestart`) makes the daemon broadcast `daemonRestarting {port,url}` (the new port from a fresh `readConfig()`), call `onRespawn`, then close+exit after 500ms; `onRespawn` spawns a replacement via `spawn(process.execPath, [...process.execArgv, process.argv[1]], ...)` (reconstructing the original launch - critically `process.execArgv` keeps the **tsx loader** flags when run as `yarn daemon` = `tsx src/backend/daemon.ts`, so the replacement is not a bare `node src/...ts` that would crash on TS; for the compiled `out/backend/daemon.js`, `execArgv` is empty) with `ARGUS_DAEMON_FORCE_START=1` which **skips the single-instance guard** and **retries `EADDRINUSE`** (up to ~5s) so it can wait for the outgoing daemon to release the (possibly same) port; the outgoing daemon sets a `handingOff` flag so its exit cleanup does **not** clear the discovery file (the replacement owns it). `startServer` now rejects its promise on a listen error so the replacement's retry loop sees `EADDRINUSE`. The **extension is connect-only but auto-starts the daemon**: `activate()` no longer hosts a server (`deactivate()` is a no-op); `extension.ts` exports `readDaemon()` (reads the discovery file fresh each call; returns undefined when the file's pid is dead so a stale file doesn't block a respawn), `ensureDaemon(extensionPath)`, and `restartDaemon(extensionPath)` (hard-kill + clear + force-spawn, for the Settings "Apply" button). `ChatPanel.buildWsUrl()` builds `ws://localhost:<port>/agent?nonce=...&dir=...` from the discovery file, or - when the daemon is down - calls `ensureDaemon()` and returns `''`. `ensureDaemon` launches the compiled `out/backend/daemon.js` **windowless/detached** via `spawn(process.execPath, [daemonJs], { detached:true, windowsHide:true, stdio:'ignore', env:{ ...process.env, ELECTRON_RUN_AS_NODE:'1' } })` + `child.unref()` (Electron-as-Node, so no separate Node install needed; the daemon is native-dep-free); it's guarded by an `isProcessAlive` check plus a 5s debounce, and the daemon's own single-instance guard makes concurrent launches safe. So opening a panel with no daemon spawns one and the overlay's retry loop (`needWsUrl`) connects once it's listening - no manual `start-argus-daemon.bat` needed (that and `yarn daemon` remain as manual/dev options). The daemon still self-exits ~10 min after the last panel closes. When `chat.html` has no URL it shows a **"Argus daemon not running"** overlay (`#daemon-down`, with a Retry button and the launch hint) and asks the extension for one via a `needWsUrl` message; the extension replies with a `wsUrl` message (the webview CSP blocks HTTP, so only the extension can re-resolve the nonce). **Daemon-restart recovery (nonce refresh)**: on WS close the bridge backs off then re-requests the URL (`requestWsUrl`) rather than reconnecting the stale baked URL, so a restarted daemon's new port/nonce is picked up; `applyWsUrl('')` keeps the overlay up and retries. The dev path (`server/index.ts` + `webview/index.html`'s `/nonce` XHR) is unchanged and not idle-killed. **A daemon is spawned from the install directory of whichever panel first needed it** (`ensureDaemon(extensionPath)`), so the process serving every panel may come from the repo's `out/` (Extension Development Host), or from any `~/.vscode/extensions/local.argus-<version>/` still installed - old installs accumulate and can win the respawn race, which is what the Info tab's `(stale)` Server row detects. Rebuilding this repo does not affect a daemon launched from an installed folder; restart it (`yarn daemon:stop`, then touch a panel) and confirm the `version` in `~/.claude/argus-daemon.json`. See [!notes/common/backend-restart.md](!notes/common/backend-restart.md) for the full restart procedure, what needs `yarn build` vs `yarn compile`, and the detached target-first swap script (`!notes/common/scripts/restart-daemon-detached.js`) for restarting from **inside** an Argus conversation - the answering CLI is a child of the daemon, so a direct `daemon-stop` aborts the requesting turn, and plain kill-then-start loses the respawn race to any still-open old-install window

- Background tasks: CLI `run_in_background: true` Bash tools produce `task_started`, `task_updated`, `task_notification` system events; server tracks pending tasks in `pendingBgTasks` Set and `totalBgTasks` counter (both reset at each user-initiated turn); `done` event includes `pendingBackgroundTasks` and `totalBackgroundTasks` when tasks are pending; reducer creates `background_waiting` outcome messages with `bgTasksCompleted`/`bgTasksTotal` on `UIMessage`; **a turn that leaves background tasks behind is a finished turn** - the reducer commits it exactly like any other (`streaming: null`, `isStreaming: false`, `turnCompletions + 1`), so the completion sound and notification fire, Stop disarms, and `background_waiting` means "finished, tasks outlived it" rather than "still busy". It used to keep a synthetic `streaming.backgroundWaiting` state alive instead, claiming the session was still working until *some later turn* ended - and a task that never ends (a browser launched for CDP, a watcher, any long-lived server) left the "Waiting N background tasks" spinner running forever with nothing able to clear it but Stop or a new message. This mirrors the CLI's own protocol, where a `run_in_background` tool returns immediately, the turn continues and ends, and the task announces itself later through a `task_notification` turn (the CLI surfaces the pending set passively under `/tasks`, never as a spinner). The still-pending tasks are recorded on the message instead: `ChatMessage` renders `BackgroundTasksNote` (`data-testid="background-tasks-note"`), a **static** line - "1 background task still running", or "2 of 3 background tasks still running" when the total is known - with no dots, no animation and no ticking timer, because Argus cannot tell a build that will finish from one that never will, and anything that animates is a promise about the future it cannot keep. Polling is **activity-gated**, because the windows only move while tokens are being spent: `noteUsageActivity()` (called from `handleSend` for every send - including a mid-turn inject and a silent retry - and from `getAccountUsage {force:true}`, plus once at daemon startup) stamps a clock and, if polling was paused, resumes it with an **immediate** fetch; the interval then re-polls every `USAGE_POLL_INTERVAL_MS` (60s) and clears itself once `usagePollActive(lastActivityAt, now)` reports the `USAGE_ACTIVE_WINDOW_MS` (1h) window has closed, so a quiet machine makes zero requests until the next turn. `lastActivityAt === 0` ("nothing yet") is deliberately distinct from a stale stamp, so a daemon nobody uses never polls on a timer. - Process lifecycle - **detach before kill, everywhere**: `/clear` and `stop` both clear `currentProc`/`currentProcKey` *before* `killProc()`, and `attachProcHandlers` guards stdout, stderr accumulation and the entire `close` body with `detached()` (`s.currentProc !== proc`). Without the detach, a `/clear` surfaced the force-killed exit code as a spurious "Something went wrong" block, and a **send issued right after a stop was taken for a mid-turn inject** (`handleSend`'s first branch tests exactly `currentProc?.stdin?.writable && !cliDone`), wrote into a pipe nobody reads, and the pending `close` then ended the fresh turn with a bare `done` - a ~1s empty turn, only "sometimes" because it depends on landing inside that window. `handleStop` therefore also broadcasts `done` itself rather than relying on the close event (the old `s.userStopped` flag existed only for that and is gone). The CLI persists each conversation as `~/.claude/projects/<encoded-cwd>/<sessionId>.jsonl`, where the cwd is encoded by replacing every non-alphanumeric char with `-` (e.g. `d:\_Projects\argus` -> `d---Projects-argus`, no separator collapsing); `src/backend/sessions.ts` resolves that folder (tolerating drive-letter case via a case-insensitive `readdir` fallback). `listSessions(workspaceDir)` scans each `*.jsonl` for the latest title (a user-set `custom-title` takes precedence over the AI-generated `ai-title`, matching the official client) and `last-prompt` (subtitle), sorts by `mtime` desc, returns `{ id, title, lastPrompt, updatedAt, lines }[]`; the WS reply `sessionList` also carries `currentId` (the live `s.sessionId`) so the modal highlights the active row with a green background (`.rowCurrent`, `--user-msg-bg`; no "current" text badge). `lines` is a per-session size metric: `readSessionMeta` sums, in its single transcript read, the newline-delimited lines of all text/code content (user text, assistant text, thinking, tool_use inputs, and tool_result output; base64 images skipped) via `countMessageLines`/`countInputLines`. Both Session History tabs render it as a fixed-width, right-aligned `.rowCount` cell just before the time (mirrors `WorkspaceHistoryModal`'s session-count column; the time cells got a fixed `min-width` so the counts line up), formatted compactly by `fmtLines` ("206", "1.2k"); shown only when `> 0`. e2e: `e2e/session-history-line-count-integration.spec.ts`. `loadSession(id, workspaceDir)` replays the transcript into webview `UIMessage[]`: consecutive `assistant` lines merge into one message (interleaved `thinking`/`text`/`tool_use` blocks) until the next real user input; `tool_result` blocks attach to their `tool_use` by id; pure-`tool_result` user lines do not create user bubbles; user `image` blocks are preserved. `resumeSession {id}` (session.ts `handleResumeSession`) sets `s.sessionId = id` (next send spawns with `--resume`), emits `sessionLoaded {id, messages}` per-client (other clients unaffected), and then calls `channel.replaySnapshot(ws)` so any in-progress streaming indicator is restored after the reducer clears it; does NOT kill `currentProc` (the active CLI turn belongs to the whole channel). `deleteSession {id}` removes the `.jsonl` (and sibling data folder) then re-sends `sessionList`; the modal also removes the row optimistically. `renameSession {id, title}` (sessions.ts `renameSession`) **appends** a fresh `{type:'custom-title', customTitle, sessionId}` line to the transcript (matching the official client's manual-rename format, so renames sync both ways; no full rewrite; `readSessionMeta` keeps the last `custom-title`, which outranks `ai-title`, so the appended line wins on the next `listSessions`), title is newline-stripped and capped at 200 chars, then re-sends `sessionList`; each row has a hover-reveal pencil (edit) button beside the trash button (both absolutely positioned at the right edge, replacing the time on hover) that opens an inline `<input>` (`.renameInput`) prefilled with the title - Enter/blur commits (optimistic local update + WS send), Escape cancels without closing the modal (the modal's `useEscapeKey` no-ops while `editingId` is set). The modal header has a refresh icon (Feather refresh-cw) beside the close button that re-sends `listSessions` and spins (`.refreshing`) until the next `sessionList` reply lands. **List caching**: both tabs' rows are cached at module scope in `SessionHistoryModal.tsx` (`wsCache`, keyed by workspace path so a switched workspace never shows the old project's sessions, and the global `allCache`), so reopening the modal paints the previous rows instantly instead of flashing "Loading..." while the server re-reads up to 200 transcripts for the global tab. The cache is never authoritative: closing invalidates it, so every open re-requests the workspace list on mount (and the global list on its first tab visit, `loadAllOnce`) and the reply overwrites the cache. Because rows are already on screen, that fetch is a background revalidate: `refreshing`/`allRefreshing` are seeded from the cache so the wait shows on the header refresh icon instead of blanking the list. Optimistic delete and rename write through via `applySessions`, and `resume`/`resumeGlobal` call `markCurrent(id)` so the cached green highlight follows the session the user just picked rather than staying on the previously-current row. Page-scoped and never persisted (unlike the tab selection, which lives in `dialogState`). **Running marker**: a session with a turn in flight right now shows a pulsing green dot before its title in both tabs (`RunningDot`, `.runningDot`, aria-label "Working now", same green and 1.5s pulse as a pending tool call), and each row carries `data-session-id` so tests can target one session. The set comes from the server, not from the list rows: `listActiveSessions()` (channel.ts) walks every entry of every workspace channel and reports those whose `state` has a sessionId, a live `currentProc` and `cliDone === false` (`currentProc` alone is not enough, a finished turn keeps its process for reuse; `!cliDone` alone is not either, a fresh entry starts with it false and no process). `notifyActiveSessions()` pushes `activeSessions {sessions}` to every client of every channel, coalesced onto a timer (so it reads the flags after the triggering handler finished mutating them, and one turn boundary sends one message) and skipped when the set is unchanged; it fires from the entry broadcast on `thinking_start`/`done`/`error`/`sessionId`/`clear` and from entry eviction (an abandoned mid-turn entry gets its proc killed and must stop showing as running). `App.tsx` holds the ids in state (never in the row cache, which would go stale behind a closed modal) and posts `getActiveSessions` on mount and on each `ws_status connected` (the server only pushes on change, so a reconnect needs one explicit sync). Scope is this server process: a turn running under a different daemon, or a `claude` session started outside Argus, is not marked. Security: all four validate `id` against a UUID regex and assert the resolved path stays directly inside the project dir (no traversal). New WS messages route over the WS bridge (not `VS_ONLY`), so `chat.html`/`ChatPanel` need no change. e2e tests in `e2e/session-history.spec.ts` (mock) and `e2e/session-history-integration.spec.ts` (integration); the "All workspaces" tab in `e2e/session-history-all-workspaces-integration.spec.ts` (integration: lists global sessions, search filters, clicking a cross-workspace session switches workspace + resumes + replays)
- Workspace history / switcher: the header workspace tile (`WorkspaceMenu.tsx`, `button` labelled "Switch workspace", shows the cwd basename) opens `WorkspaceHistoryModal` (centered `createPortal` modal) with two tabs. **Recent** tab: `listWorkspaces()` in `src/backend/sessions.ts` enumerates the projects the CLI has run in by scanning `~/.claude/projects/*/` and recovering each real cwd from the `cwd` field inside the transcript records (the folder name is a lossy encoding and can't be decoded), drops paths that no longer exist, sorts by latest transcript mtime, returns `{ path, name, sessions, updatedAt }[]`; the WS reply `workspaceList` carries `currentPath` so the active row is highlighted (`.rowCurrent`); a refresh icon re-scans. **Browse** tab: a real folder explorer over the whole machine backed by `listDir(target?)` (`sessions.ts`) -> WS reply `dirList {path, parent, entries}`; undefined target opens at `os.homedir()`, the empty-string sentinel (`DRIVES_ROOT = ''`) lists drive roots ("This PC" - `C:\`, `D:\`, … on win32, `/` on POSIX), and a filesystem root reports the drives root as its `parent` so the user can walk up past a drive to switch drives; directories only, sorted case-insensitively, tolerates unreadable dirs (empty list, still navigable up); the breadcrumb shows the current path (tail-truncated via `direction: rtl`), clicking a folder row navigates in, an "Up" row goes to `parent` (the up affordance is an arrow-up SVG, not a ".." label), and "Open this folder" picks the current dir (disabled at "This PC"). The breadcrumb is also **editable**: clicking it swaps the display `div` for an `input` (aria-label "Folder path") prefilled with the current path, so a folder path can be typed or pasted from the clipboard; Enter navigates there (`browseTo`), Escape/blur cancels (Escape first cancels the edit, then closes the modal via the guarded `useEscapeKey`), and the `dirList` reply clears the edit state. A bad path is auto-corrected server-side: `listDir` runs the resolved target through `nearestExistingDir()`, which walks up ancestors to the closest real directory (`C:\Users\Admi2` -> `C:\Users`, a file -> its dir, a missing drive -> `os.homedir()`), so the explorer never dead-ends on a typo. The modal is fixed at full height (`height: calc(100vh - 64px)`) with a `flex: 1` scrolling `.body`. Either tab's selection calls `onSelect(path)` -> `switchWorkspace` (App.tsx) which resets the UI and reconnects the WS with the new `?dir=` (handled in `index.html`/`chat.html`, not `VS_ONLY`). New WS messages (`listWorkspaces`/`workspaceList`, `listDir`/`dirList`) route over the WS bridge, so `chat.html`/`ChatPanel` need no change. e2e: `e2e/workspace-name-integration.spec.ts` (tile name), `e2e/workspace-browse-integration.spec.ts` (Browse folder explorer), and `e2e/workspace-browse-edit-integration.spec.ts` (editable breadcrumb: valid path navigates, invalid path falls back to nearest existing dir)
- Session architecture: `session.ts` is the thin orchestrator (WS message routing, send/stop logic); shared mutable state defined in `sessionState.ts` (`SessionState` interface + `createSessionState` factory); CLI stdout event parsing and proc lifecycle in `cliHandler.ts` (`handleCliEvent` dispatches by event type to focused handler functions: `handleSystemEvent`, `handleDelta`, `handleAssistant`, `handleToolResult`, `handleUserEvent`, `handleResult`); watchdog and login extracted as standalone modules returning handler objects; all modules receive `SessionState` reference for shared access
- Config cache: `readConfig()` uses `fs.statSync` mtime check; re-reads file only when mtime changes; external edits to `~/.claude/argus.json` take effect without server restart
- appendSystemPrompt config: `appendSystemPrompt` field in `ArgusConfig` (default `''`) passes `--append-system-prompt <text>` to every CLI spawn when non-empty; useful for injecting extra context or test-specific instructions; set in `e2e/argus.json` for e2e overrides
- effort/thinking config: `effort` (string, default `'high'`) and `thinking` (boolean, default `true`) in `ArgusConfig`; when `thinking` is false, `--effort low` is passed regardless of `effort`; when `thinking` is true and `effort` is non-empty, `--effort <effort>` is passed; uses nullish coalescing (`??`) not logical OR (`||`) so an explicit `effort: ""` correctly passes no effort flag (empty string is a valid "use CLI default" signal)
- File path linkification: `linkifyPaths()` in `utils/filePath.tsx` skips strings longer than 5000 chars (`MAX_LINKIFY_LENGTH`) to prevent regex backtracking on adversarial LLM output
- E2e tests: Playwright-based, split into two projects in `playwright.config.ts`; `mock` project matches files without `-integration` suffix, runs first with 4 workers using `window.dispatchEvent` to inject messages, no Claude CLI needed; `integration` project matches `*-integration.spec.ts` files (regex `/-integration\.spec/`), runs after mock finishes (`dependencies: ['mock']`) to avoid OOM from concurrent CLI processes + Chromium instances; naming convention: integration tests must have `-integration` suffix (e.g. `chat-integration.spec.ts`), mock tests must not; `waitForApp()` in `e2e/helpers.ts` navigates with `waitUntil: 'domcontentloaded'` and retries `page.reload()` up to 3 times if React fails to mount; Chromium launched with `--disable-gpu --disable-dev-shm-usage --no-sandbox` for reduced memory; **one flat timeout for every test**: the global `timeout: 30_000` in `playwright.config.ts` applies to both projects, mock and integration alike, with `retries: 0` on `integration` so a hang isn't paid twice (the `mock` project keeps the global `retries: 1` for transient failures); this replaced an earlier `integration`-only `timeout: 90_000` override, which was too generous - a real CLI turn normally finishes in a few seconds, so a genuine hang still cost close to 90s before being reported, and nothing passing was using that headroom (the full 112-test integration run completes in ~5 min at the flat 30s, faster than the old tiered run); a per-test `test.setTimeout(...)` override is now allowed as a rare, explicitly-commented exception for a test that provably needs more (e.g. `session-browse-during-stream-integration.spec.ts`'s three-real-CLI-turn test uses `60_000`) - this reverses the old blanket "no per-test overrides" rule, which only held because 90s never needed one; `fullyParallel: true` for maximum parallelism within each project (the `integration` project uses `workers: 1` - each test drives a real Claude CLI + a Chromium instance against the one shared `:3001` backend; 2 workers causes the backend to die mid-run (resource exhaustion combined with concurrent writes to `e2e/argus.json` from parallel test workers), cascading into 40+ failures; 1 worker completes the full suite in ~7 min, actually faster than 2 workers with cascades); the integration server reads `e2e/argus.json` (via `ARGUS_CONFIG`) as its full settings config, including the webview toggles (`showLogs` etc.) the webview hydrates over `getSettings` - keep `showLogs: true` there (the `log-autoscroll-integration` test needs the panel mounted; flipping it false hangs that test waiting for `[data-testid="log-list"]`); `clickAndWaitForModal()` in file-path-links uses `toPass()` retry loop for WS roundtrip tolerance; run `yarn test:clean` manually before the suite if stale processes are suspected (test-clean.js kills orphaned claude --print agents, stale Vite/dev servers, Playwright runners + chromium, stray test daemons; protects this session's ancestor chain and the real daemon's whole process subtree (live sessions' CLIs); flags: `--dry`, `--no-claude`); interactive scripts (`test:e2e:ui`, `test:e2e:debug`) and `test:e2e:report` do not auto-clean. **Config guard for a reused dev server**: `webServer.reuseExistingServer: true` means a `yarn dev` the user already had running (started without `ARGUS_CONFIG`) gets adopted as the backend and then reads/writes the real `~/.claude/argus.json` instead of `e2e/argus.json` - tests fail against settings they never set, for reasons invisible in their output. `e2e/global-setup.ts` catches this before any test runs: it hits a loopback-only `GET /health` (`src/backend/index.ts`, returns `{configPath, pid}` to `127.0.0.1`/`::1` only, 403 otherwise) and throws immediately if `configPath` doesn't match the resolved `e2e/argus.json` (case-insensitive on `win32`); a server not yet reachable is not an error (a Playwright-started server always gets the right env). **Diagnosing bulk integration failures**: many integration specs failing at once is usually one cascade, not N bugs - the signature is that they share the page state `"Disconnected, reconnecting..."` and fail in run order from some point onward, meaning the shared `:3001` backend died mid-run. Playwright's `webServer` swallows backend stdout, so debug with the server owned outside the runner (`yarn dev > /tmp/be.log 2>&1 &` then `npx playwright test --project=integration --no-deps`) and check the log for `spawn UNKNOWN` / a `handleSend` stack. The look-alike is a **dev-server handover**: `reuseExistingServer: true` also adopts the still-shutting-down server of your *own* previous `npx playwright test`, and when that one exits the rest of the run fails at `page.goto` with `ERR_CONNECTION_REFUSED` on `:5173` (Vite gone, not just the backend) while `test-clean --dry` finds nothing to kill - wait until neither port has a `LISTENING` socket before re-running. **Copy `test-results/<folder>` out before any re-run**: Playwright wipes that directory at the *start* of every run, even a single-spec one, and its `error-context.md` a11y snapshot carries the app's Debug Log (raw CLI stdout events with timestamps), which usually settles app-vs-CLI questions with no re-run at all; for a flaky test it is the only record that exists. **Writing stable integration assertions**: gate on app-owned state, not model-owned output - use the Stop button (rendered for every active turn) rather than a `[class*="toolCall"]` locator (whether the model calls a tool is its own choice, so it intermittently never appears), and branch on whether the turn is still live via `stopBtn.waitFor({ state: 'visible', timeout })` rather than `isVisible()` (an immediate check that ignores its `timeout` option, so right after a UI transition it reports `false` for a stream that *is* live and sends the test down the wrong branch); never assert on data a code path cannot produce - after a **disk replay** (`loadSession` sets only `outcome: 'success'`, no `responseTime`/token fields) there is no timer element at all, so a "stream already finished" branch must `test.skip(...)` instead of asserting token counts. **CLI memory pollution**: the CLI auto-loads `~/.claude/projects/<encoded-cwd>/memory/` into every session it spawns, so tests asserting a reset session has *forgotten* something must generate the token per run (never hard-code it), must avoid the word "remember" in the prompt (the agent obeys by writing it to the memory file, polluting the user's real memory), and must forbid tools in the recall prompt. Full details in [!notes/common/e2e-testing.md](!notes/common/e2e-testing.md) and [!notes/issues/integration-suite-cascade-crash.md](!notes/issues/integration-suite-cascade-crash.md)

```sh
yarn dev          # starts Vite frontend (port 5173) + WebSocket server (port 3001) in parallel
yarn dev:frontend # Vite dev server only (no backend)
yarn dev:server   # WebSocket server only (tsx server/index.ts)
yarn daemon       # run the always-on daemon (tsx src/backend/daemon.ts); fixed port 3017, 10-min idle-exit
yarn daemon:stop  # stop the running daemon (node scripts/daemon-stop.js; idempotent)
yarn build        # bundle React webview to media/webview.js + media/webview.css
yarn watch        # watch + rebuild webview on save (for VS Code Extension Host testing)
yarn compile      # compile extension TypeScript
yarn watch:tsc    # watch mode for extension TypeScript
yarn test:e2e     # run Playwright e2e tests (starts dev server automatically)
yarn test:e2e:integration # run only integration tests (skips mock dependency)
yarn test:e2e:headed # run e2e tests with visible browser
yarn test:e2e:ui  # open Playwright UI mode
yarn ctx:install  # add "Open Argus" to Windows Explorer context menu (requires elevated shell)
yarn ctx:uninstall # remove context menu entry
# Primary UI testing: use `yarn dev` + browser refresh - do not suggest reloading VS Code extension
```
