# Messages in the transcript that the user never sent

| | |
|---|---|
| Reported | 2026-09-06, screenshot of a live session in `d:\_Projects\scub111g\people-agent` |
| Transcript | `C:\Users\Admin\.claude\projects\d---Projects-scub111g-people-agent\cfd1ee0d-2b09-4779-b148-6caaddd1771f.jsonl` |
| Produced by | Claude Code, model claude-opus-5 |
| Status | Fixed, spec verified red then green. Not committed |

## Symptom

A session reading a scanned document showed a bubble after every image `Read`:

```
[Image: original 2122x3135, displayed at 1354x2000. Multiply coordinates by 1.57 to map to original image.]
```

Thirteen of them in that one turn. They render exactly like something the user typed, which
is what prompted the question of whether the agent was quietly sending requests of its own.

It is not the agent. The **Claude CLI** writes user-role messages of its own, and Argus was
rendering all of them.

## Root cause

`Uat()` in the CLI bundle builds that note from the resize dimensions, and the FileReadTool
path attaches it to the conversation as a user message tagged `isMeta`:

```js
let $ = D.file.dimensions ? Uat(D.file.dimensions) : null;
return { data: D, ...$ && { newMessages: [Rn({ content: $, isMeta: !0 })] } }
```

When the CLI serialises events for the SDK stream it maps that to a documented field
(`isSynthetic` appears in the bundle's own zod schema for the `user` event):

```js
case "user": yield { type: "user", message: o.message, …, isSynthetic: o.isMeta || o.isVisibleInTranscriptOnly, … }
```

Argus checked neither field:

- **Live** - `handleUserEvent` (`src/backend/cliHandler.ts`) broadcast `user_inject` for
  every `text` block in a `user` event.
- **Replay** - `loadSession` (`src/backend/sessions.ts`) pushed a `role: 'user'` message for
  any user record with text, so resuming the session from Session History showed the same
  phantom text as full user bubbles.

Note the transcript record stores the note as a plain **string** while the stream delivers
it as a **text block**; the live path is the one in the screenshot (the turn carries a real
timer and token counts, which a disk replay never has).

## Probes

`scripts/probe-cli-image.js` drives a real CLI with Argus's own spawn flags over a generated
2200x3200 PNG (`scripts/make-big-image.js`) and dumps every stdout event with base64 elided.
Two `user` events come back per image Read:

| event | flag | content |
|---|---|---|
| tool result | none | `tool_result` -> `image` block |
| the note | `isSynthetic: true` | `text` block, the `[Image: original …]` string |

So the flag, and not the text, is the discriminator - which matters because the same
mechanism carries entirely different wording elsewhere.

`scripts/probe-inject-echo.js` closes the one path the fix could plausibly have broken - a
real mid-turn inject, written into the stdin of a turn already running. The CLI answered it
(`num_turns: 2`) and emitted **no** synthetic user event for it; the only `user` event in the
whole turn was the tool result, `isSynthetic=undefined`. So the gate cannot swallow an inject.

## What the flag actually covers (the reason the first fix idea was wrong)

`scripts/audit-meta-users.js` bucketed every user record across the **1,885 transcripts** on
this machine: 42,204 ordinary user records, **707 CLI-authored** ones. Image notes are a
minority of them:

| count | content |
|---|---|
| ~370 | `Base directory for this skill: … # Skill …` - the body a slash command expands into |
| 197 | `Continue from where you left off.` |
| 99 | `[Image: original …]` / `[Image source: …]` |
| 4 | `This session is being continued from a previous conversation…` (compact summary) |
| 2 | `<local-command-caveat>Caveat: The messages below were generated by the user…` |
| 2 | `[Your previous response had no visible output…]` |

Every bucket is text the CLI wrote. None is text a human typed, so suppressing on the flag is
sound - and a fix that had special-cased the `[Image: …]` prefix would have left the other
~600 bubbles in place.

`scripts/audit-edge-cases.js` then found the two cases that shape the fix:

1. **4 records carry an image *and* CLI text** - a `/skill` invocation that had an image
   pasted with it. Dropping the record whole would lose the user's own image, so the gate is
   **per block**, not per event. Same reason the `tool_result` branch stays unconditional.
2. **`isVisibleInTranscriptOnly` occurs on its own** (4 records, all compact summaries;
   703 have `isMeta`, 0 have both). The replay check has to OR them, exactly as the CLI's own
   stream mapping does.

## Fix

- `src/backend/cliHandler.ts` - `handleUserEvent` skips the `user_inject` broadcast when the
  event carries `isSynthetic`; `tool_result` blocks are unaffected.
- `src/backend/sessions.ts` - `isCliAuthoredUser()` (`isMeta || isVisibleInTranscriptOnly`),
  the user-role counterpart of the existing `isSyntheticPlaceholder`. String content is
  skipped; text blocks are skipped; **images are kept**.

`e2e/synthetic-user-message.spec.ts` drives the compiled `handleCliEvent` and `loadSession`
directly - no page, no CLI, since the question is which frames one stdout sequence emits and
which messages one transcript replays into. Payloads copied from the probe. Verified red
against the unfixed tree (2 of 3 failing), green after. Controls, without which a blanket
"suppress all user text" would pass: a real mid-turn inject still renders, a tool result
inside a synthetic envelope is still delivered, and the pasted image survives the replay.

## What an image Read looks like after the fix (observed, not derived)

Driven through the real UI on the dev server (`?dir=` a temp folder holding a generated
2200x3200 PNG, one real CLI turn), screenshot in `after-fix-chat.png`:

- the `Read <path>` row stays, with the path still a link;
- the `[Image: original …]` bubble under it is gone, and nothing takes its place;
- clicking the path still opens the image in the previewer, fetched per click by
  `readToolImage` from the transcript.

So the note is removed rather than replaced. The tool result behind the row still holds the
`[image image/png 305 KB]` marker `stringifyToolResult` puts there, which is a separate,
older mechanism and is unchanged by this fix.

## Known and deliberate exclusion

`[Request interrupted by user for tool use]` (52 occurrences in the corpus) is **not** flagged
by the CLI, so it still renders as a bubble. It is left alone: it marks a real thing the user
did, and the official client shows it too. Suppressing it would need a text match, which is
what this fix exists to avoid.

## Superseded

- **Was:** the three flags are the complete set of marks for a CLI-authored user message -
  `isSynthetic` on the stream, `isMeta` / `isVisibleInTranscriptOnly` in the transcript.
- **Actually:** a background task's completion prompt is CLI-authored and carries **none** of
  them. Its mark is `origin.kind === 'task-notification'`, the field `handleResult` already
  trusted on the result event. Replaying a CI watch therefore showed 42 raw
  `<task-notification><task-id>…</task-id>` bubbles out of 115.
- **Why it was wrong:** the 1,885-transcript audit counted the records that *had* the flags
  and never asked which CLI-authored records lacked them. The live path hid the gap by
  accident (the event lands before `thinking_start`, so the reducer drops the `user_inject`
  for want of streaming state), so the only symptom was on replay, which was not the path
  under test.
