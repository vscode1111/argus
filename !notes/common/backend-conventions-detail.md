# Backend and session conventions

Detailed conventions moved from `AGENTS.md`. Verify implementation details against current code before relying on a historical example.

- Win32 focus: `win32Focus.ts` uses `koffi` FFI; `captureForegroundWindow()` is called on panel creation (caches the VS Code HWND), `focusCachedWindow()` on notification click via the `focusPanel` webview message and from `ChatPanel.revealForActivation()` (the toast click-to-focus URI handler). `focusCachedWindow()` first defeats the Windows **foreground lock** (briefly zeroes `SPI_SETFOREGROUNDLOCKTIMEOUT` + `AllowSetForegroundWindow(ASFW_ANY)`, restored in finally) - without this a background process's activation is demoted to a flashing taskbar button instead of an actual switch; it then calls `SwitchToThisWindow` (the Alt+Tab API, which crosses **virtual desktops** - `SetForegroundWindow` and the `vscode://` protocol launch do not) inside the `AttachThreadInput` dance with `BringWindowToTop`/`SetForegroundWindow` so the window is raised even when already on the current desktop

- Multi-session shared channels: clients connecting with the same `?dir=` join one `ChannelData` (keyed by workspace dir). `channel.ts` holds a `Map<workspaceDir, ChannelData>` registry. Each `ChannelData` contains a `Map<key, SessionEntry>` of concurrent sessions and a `Map<WebSocket, SessionEntry>` routing table. **SessionEntry** holds: `state: SessionState`, `clients: Set<WebSocket>`, `browsingClients: Set<WebSocket>` (clients viewing a different transcript via `resumeSession`), `history: ChannelMessage[]` (MAX 200), `snapshot` (in-progress streaming state for late-join replay), and `lastActivityAt`. Each entry has its own broadcast function (scoped to that entry's clients). **Session lifecycle**: new clients join the most recently active entry (`defaultEntry`); `newSession` calls `channel.moveToNewSession(ws)` which creates a fresh `SessionEntry` for just that client - the old entry and its CLI proc keep running (other clients continue to see the turn). When the last client leaves an entry, the watchdog is stopped and a 30s grace timer starts; the proc is NOT killed during the grace window (it runs on, broadcasts go to zero clients, and a returning client can rejoin). **When the timer actually evicts the entry, `scheduleEntryCleanup` calls `killProc(entry.state.currentProc)`**: an evicted entry is unreachable (no client can rejoin it), so without this its CLI process lingers for the life of the server. That leak was severe once `addClient(ws, fresh)` gave each browser client its own entry - every abandoned entry leaked a `Codex` process until the OS refused new spawns (see `!notes/issues/integration-suite-cascade-crash.md`). **SESSION_STREAM_EVENTS gating**: `thinking_start`, `text_chunk`, `tool_start`, `tool_end`, `done`, `error`, `message`, `user_inject`, `token_update`, `retry_*`, `contextUsage` are suppressed for browsing clients (those in `entry.browsingClients`); control events (`clear`, `modelChanged`, `log`, etc.) always reach all clients. **Two-send-path rule**: broadcast events use `s.broadcast()` (entry-scoped, gated for browsing clients); per-client responses (`settings`, `skills`, `filePreview`, `accountUsage`, `sessionList`, `clientCount`, `serverInfo`, etc.) use `ws.send()` directly. `switchModel`/`switchEffort`/`switchThinking` are global settings: they use `channel.forEachSession()` to update all entries' states and `channel.broadcastToAll()` to reach every client across all entries. `index.ts` calls `getOrCreateChannel(workspaceDir)` then `attachClientHandlers(ws, channel, MODEL, hooks)`. First client on an entry triggers `initChannelSession` (sets `s.sendLog`, watchdog, `emitSyntheticSend`); later clients skip that block (`!s.sendLog` guard). e2e coverage in `e2e/shared-channel-integration.spec.ts` (broadcast, late-join replay, per-client isolation, isolated newSession, model broadcast, workspace isolation, Bug 1 no-kill-on-resume, Bug 2 browsing-client stream gating)

- Send while browsing another session: a send from a client that navigated away via `resumeSession` belongs to **the session it is looking at**, not to the turn still streaming in the entry it left. `handleSend` only ever receives the entry `SessionState`, never the `ws`, so it cannot tell a browsing client from a live one - left in place, its mid-turn-inject branch (`s.currentProc?.stdin?.writable && !s.cliDone`) fired purely because the *entry* had a live proc, and the text was written into the other session's stdin. The sender saw nothing back (`user_inject` and `message` are both in `SESSION_STREAM_EVENTS`, gated away from browsing clients) while every client watching that session got the stray prompt as an inject bubble. Fix: `handleResumeSession` records the browsed id via `setBrowsing(ws, true, id)` into `ChannelData.clientViewing` (the entry's own `sessionId` deliberately still points at the streaming session, to keep its `--resume` arg correct, so nothing else remembers what the user has on screen), and the `send` handler calls `channel.detachToBrowsedSession(ws)` **first** - moving the client into its own entry bound to that id (transferring `owner` exactly as `moveToNewSession` does, so a later reconnect rejoins the session the user is actually in). The new entry has no proc, so `handleSend` takes the normal spawn path with `--resume <browsed id>`, and the session left behind keeps streaming untouched. `clientViewing` is cleared on `setBrowsing(ws, false)`, `moveToNewSession`, `detachToBrowsedSession` and `removeClient`. e2e: `e2e/browse-send-routing-integration.spec.ts` (the browsed send starts a real turn and produces no `user_inject`; a second client watching the live session never receives it) - both raw-WS, because "browsing" only exists while a real CLI process is mid-turn

- Resuming a session that is streaming in another entry: `handleResumeSession` calls `channel.attachToLiveSession(ws, id)` **first**. Without it the handler only ever rebound the client's **own** entry's `sessionId` and replayed **that** entry's snapshot, so a session mid-turn in a different entry (a second panel, or - since the browse-send fix - the entry the client detached from) was served from `loadSession`: the transcript on disk stops at the last committed turn, so the client got a stale view with **no progress indicator and no further output**, while the turn ran on invisibly. `attachToLiveSession` scans for an entry whose state has that `sessionId` with a live `currentProc` and `cliDone === false`, skipping the client's current entry (already being there is an ordinary return-to-live resume, which the existing branch replays itself), and `joinEntry`s the client so it receives that entry's history + streaming snapshot. The handler then sends a `token_update` (the snapshot replay restores the blocks but not the counters behind the timer) and returns before the disk-load path. e2e: `e2e/resume-live-session-integration.spec.ts`

- Session deep link: a session is addressable by URL - `http://<host>:<port>/?session=<id>` (`?dir=` optional). At WS upgrade (`src/backend/index.ts`) the server resolves the id to its workspace via `findWorkspaceForSession(id)` in `sessions.ts` (scans `~/.Codex/projects/*/<id>.jsonl` and recovers the transcript's recorded `cwd`; UUID-validated so a malformed id never reaches the filesystem) **before** `getOrCreateChannel` - the resolved workspace **wins** over `?dir=` (a dir copied between machines can be stale; the mismatch is logged, not fatal), and an unresolvable id is dropped so the connection falls back to `?dir=` alone. `channel.addClient(ws, fresh, sessionId)` live-attaches the socket to the entry currently bound to that sessionId (overrides `fresh`); when no live entry owns the id, the fresh entry gets `s.sessionId = id` (idle entries only) so the next send spawns with `--resume`. The initial replay is deferred to the client's `webviewReady` message - the WS opens during React module evaluation, so an upgrade-time replay could be dispatched before `App` registers its `message` listener: on `webviewReady` the server pushes `workspaceInfo` (resolved path; `App.tsx` skips the optimistic `?dir=` paint when a `session` param is present so the tile never flashes a wrong project name) then either `channel.replayHistory(ws)` (live: entry history + streaming snapshot, so the linked page lands mid-stream with a live Stop button and no click) or a disk `loadSession` -> `sessionLoaded`. Both browser shims (`webview/index.html`, `media/browser.html`) forward `?session=` into the WS URL and keep it in step with navigation (cleared on `switchWorkspace`/`newSession`, updated on `resumeSession`, and synced to the browser URL via `history.replaceState()` on each change) so the address bar always reflects the current session and a WS reconnect re-attaches to what the user is viewing. Session History rows have a hover-reveal copy-link button (browser mode only, `!isVsCode`) that copies `<origin>/?session=<id>` (async clipboard API with a hidden-textarea fallback - plain-http LAN pages are not a secure context). A brand-new chat has no id until the CLI assigns one, so `handleSystemEvent` (`cliHandler.ts`) broadcasts a `sessionId {id}` event on the `init` subtype when the id changes; both browser shims listen for it and `updateUrl()`, so a fresh conversation becomes shareable/reloadable without a click. `sessionId` is in `SESSION_STREAM_EVENTS` (a browsing client is viewing another transcript and must not have its address bar rewritten). Reload of a deep-linked **finished** session used to land on a blank page: the first load bound an entry to the id but filled it from disk, so the entry's in-memory history was empty and re-attaching replayed nothing. `channel.replayHistory()` now returns `false` when the entry has neither history nor a snapshot, and `session.ts` falls back to `loadSession` in that case. e2e tests in `e2e/session-deep-link-integration.spec.ts` (live attach + remote stop, no-dir workspace resolution + disk replay, new-chat id lands in the URL, reload of a finished deep link replays again, stale-dir override, malformed-id fallback)

- Per-panel session isolation: extension panels pass a stable `?panel=<uuid>` (`ChatPanel.panelId`, `crypto.randomUUID()` per panel, constant for the panel's lifetime) so each panel gets its **own** `SessionEntry` instead of joining the workspace's `defaultEntry` - without it two panels in one workspace shared a conversation and echoed each other's turns. `SessionEntry.owner` records the panel id; `addClient(ws, fresh, sessionId, panelId)` rejoins the owned entry when the id is known (webview reload, daemon restart) and creates one when it isn't. A rejoin returns `true` like a deep-link attach (replay deferred to `webviewReady` for the same mount-timing reason) - `session.ts` splits the two via `liveAttach = attached && !!hooks.sessionId` vs `panelRejoin = attached && !hooks.sessionId`, and the rejoin branch replays entry history or falls back to `loadSession` when the entry was resumed from disk. `moveToNewSession` transfers `owner` to the new entry so a later reconnect rejoins the new session, not the abandoned one. e2e: `e2e/panel-isolation-integration.spec.ts`

- Unified WebSocket server: `src/backend/index.ts` exports `startServer({ port, model })` returning `{ httpServer, port, nonce, close }`, used by both the standalone **daemon** (`src/backend/daemon.ts`) and standalone dev mode (`server/index.ts`, port 3001); `ChatPanel` injects the WS URL (`ws://localhost:PORT/agent?nonce=...&dir=...`) into `chat.html`; the webview connects via a shim script that routes Codex-related messages to WS and VS Code-specific messages (`openFile`, `openUrl`, `focusPanel`, `getInfo`, `readFilePreview`, `copyImage`, `needWsUrl`) to real `postMessage`; `scripts/dev.js` starts both Vite and server in parallel, watches `server/` and `src/backend/` for auto-restart

- Shared WS bridge factory: the reconnect / message-queue / dispatch / visibility-reconnect machinery for **all three** webview hosts lives once in `webview/public/ws-bridge.js` as `window.createArgusBridge({ nextUrl, onStatus })` -> `{ post, reconnectNow, reconnectIfIdle, isReady }` (classic script, runs before the React bundle which calls `acquireVsCodeApi` on mount). Source of truth is `webview/public/`; the Vite dev server serves it at `/ws-bridge.js`, and `vite build` copies it into `media/` via `publicDir` (set explicitly in `webview/vite.config.ts` since the build root is the repo cwd) so the extension webview and the daemon load the same file (`media/ws-bridge.js` is gitignored, a build artifact). Each host keeps only its small URL-resolution + routing shim and calls the factory: **dev** (`webview/index.html`, inline) resolves `ws://<host>:3001/...` with an XHR `/nonce` refresh + e2e `?mock=1` suppression; **browser/daemon** (`media/browser.html`, inline) resolves same-origin `ws(s)://<location.host>/agent` with an XHR `/nonce`; **extension** (`media/chat.html`, loads `{{wsBridgeUri}}` then an inline shim) uses the baked/extension-pushed URL (`nextUrl` returns it or null), routes `VS_ONLY` messages to the real VS Code `postMessage`, and drives the daemon-down overlay + `needWsUrl`/`wsUrl` refresh from `onStatus`. The old per-host copies (`webview/public/dev-bridge.js` and the inline IIFEs in chat.html/browser.html) were collapsed into this; e2e `ws-reconnect.spec.ts` (mock) covers the factory's reconnect behavior. **Two close codes are exempt from the ordinary backoff loop**: `4001` (`CLOSED_BY_PEER`, another panel's Connected Clients list disconnecting this one) and `4002` (`CLOSED_IDLE`, the server closing a connection for sitting idle too long - see "Idle connection timeout" above) both set `stoppedReason` (`'peer' | 'idle' | null`, replacing an earlier plain `stopped` boolean) - no backoff retry for either - and `onStatus`/`ws_status` carry that reason (`closeReason`, replacing an earlier plain `closedByPeer` boolean) so the app can say which one it was and the extension host can skip its `requestWsUrl()` (which would auto-spawn a daemon). The two reasons diverge on `visibilitychange`: it reconnects for `'idle'` (and for no reason at all, catching sleep/resume) but never for `'peer'`, or switching tabs would silently resurrect a deliberate disconnect. `reconnectNow()` clears the reason unconditionally (an explicit manual click is the way back from either), while `reconnectIfIdle()` is the automatic path and only ever fires for `'idle'`. The factory publishes `reconnectNow` as `window.argusReconnect` so the React app has one manual way back in every host; `reconnectIfIdle` is deliberately **not** published globally, since only a host's own visibility signal should call it (`chat.html`'s `panelVisible` handler, or the bridge's own `visibilitychange` listener for the two browser-tab hosts)

- Daemon-served browser UI: the shared HTTP server (`src/backend/index.ts`, used by both the daemon on 3017 and the dev server on 3001) serves the built webview directly so a plain browser can open `http://localhost:<port>/` and get the full app with no Vite. A fixed allowlist (`STATIC`: `/` -> `media/browser.html`, `/webview.js`, `/webview.css`, `/argus-icon.ico`) reads from `media/` (no arbitrary paths / traversal); `/` returns 503 with a "run `yarn build`" hint if the bundle is missing. `media/browser.html` is self-contained: it carries the Dark 2026 theme `:root` vars (no VS Code host to inject them), shims `acquireVsCodeApi()` and routes every app message over a **same-origin** WebSocket (`ws(s)://<location.host>/agent`), fetching the nonce at runtime via a synchronous `GET /nonce` XHR (re-fetched before each connect so a daemon restart recovers); there is no VS Code postMessage path here (no extension), so all messages go to the WS. Requires `yarn build` to have produced `media/webview.{js,css}`. This is independent of the Vite dev server (`http://localhost:5173`, port 3001 backend, HMR) which remains the primary UI-dev path

- Single daemon server + connect-only extension: instead of one server per VS Code window on a dynamic port, a **single shared daemon** (`src/backend/daemon.ts` -> compiled `out/backend/daemon.js`) runs on a fixed port (default `3017`; precedence `ARGUS_DAEMON_PORT` env > `argus.json` `daemonPort` > 3017, resolved in `daemon.ts` via `readConfig()`; the discovery file records the actual port so the extension + browser adapt automatically - changing it needs a daemon restart) and is started **on demand** by the user (`cmd/start-argus-daemon.bat` via windowless `scripts/daemon.vbs`, or `yarn daemon` = `tsx src/backend/daemon.ts` for dev). It **self-exits after 10 min with zero connected clients** (idle is connection-count based, so an open panel mid-turn keeps its socket open and is never killed). Idle-shutdown is opt-in via `startServer`'s `idleTimeoutMs` + `onIdleShutdown` options (default off, so the dev path on 3001 never self-exits); `startServer` itself never calls `process.exit` - the daemon supplies `onIdleShutdown = () => process.exit(0)`. The idle timer is armed both at startup (so a daemon nobody ever connects to still exits) and on each last-client disconnect, and cleared on connect. Idle precedence: `ARGUS_DAEMON_IDLE_MS` env > `argus.json` `daemonIdleMs` > 10-min default (resolved in `daemon.ts` via `readConfig()`); `ARGUS_DAEMON_FILE` overrides the discovery-file path - the env vars are used by e2e to exercise idle-exit quickly against a throwaway file. Changing `daemonIdleMs` needs a daemon restart. Daemon behavior is covered by `e2e/daemon-lifecycle-integration.spec.ts` (discovery file, nonce gate, single-instance guard, idle self-exit + file cleanup) and `e2e/daemon-browser-integration.spec.ts` (the daemon-served browser UI mounts + connects, static allowlist), with shared spawn helpers in `e2e/daemonHelpers.ts`. The daemon writes a discovery file `~/.Codex/argus-daemon.json` `{ port, nonce, pid, version, startedAt }` (mode 600), cleaned on idle-exit / SIGINT / SIGTERM / `process.on('exit')` (a hard kill leaves a stale file, handled below). Single-instance guard: on start it reads the file and exits early if the recorded **port** answers as a live daemon (idempotent launcher); a crashed daemon's stale file answers nothing, so a fresh start proceeds and overwrites it. Discovery helpers live in `src/backend/daemonInfo.ts` (`DAEMON_FILE`, `DEFAULT_DAEMON_PORT`, `readDaemonInfo`/`writeDaemonInfo`/`clearDaemonInfo`, `isProcessAlive`, `probeDaemon`, `isDaemonUp`). `clearDaemonInfo(onlyIfPid?)` is **ownership-aware**: with a pid it leaves the file alone unless that pid is the registered one, and `daemon.ts`'s `cleanup()` passes `process.pid`. Without this, a daemon that exits early (port already taken) wiped the live owner's registration and stranded the extension - it could neither connect (no file, and the nonce lives only in the owner's memory) nor respawn (port held). The `EADDRINUSE` message likewise distinguishes "pid N owns it (discovery file intact)" from an unreachable holder. **In-process self-restart** (for the browser-served "Apply" button, where there is no extension to respawn): `startServer`'s `onRespawn` option (supplied only by the daemon) + a `restartDaemon` WS message (`session.ts` -> `hooks.onRestartRequest` -> `doRestart`) makes the daemon broadcast `daemonRestarting {port,url}` (the new port from a fresh `readConfig()`), call `onRespawn`, then close+exit after 500ms; `onRespawn` spawns a replacement via `spawn(process.execPath, [...process.execArgv, process.argv[1]], ...)` (reconstructing the original launch - critically `process.execArgv` keeps the **tsx loader** flags when run as `yarn daemon` = `tsx src/backend/daemon.ts`, so the replacement is not a bare `node src/...ts` that would crash on TS; for the compiled `out/backend/daemon.js`, `execArgv` is empty) with `ARGUS_DAEMON_FORCE_START=1` which **skips the single-instance guard** and **retries `EADDRINUSE`** (up to ~5s) so it can wait for the outgoing daemon to release the (possibly same) port; the outgoing daemon sets a `handingOff` flag so its exit cleanup does **not** clear the discovery file (the replacement owns it). `startServer` now rejects its promise on a listen error so the replacement's retry loop sees `EADDRINUSE`. The **extension is connect-only but auto-starts the daemon**: `activate()` no longer hosts a server (`deactivate()` is a no-op); `extension.ts` exports `readDaemon()` (reads the discovery file fresh each call; returns undefined when the file's pid is dead so a stale file doesn't block a respawn), `ensureDaemon(extensionPath)`, and `restartDaemon(extensionPath)` (hard-kill + clear + force-spawn, for the Settings "Apply" button). `ChatPanel.buildWsUrl()` builds `ws://localhost:<port>/agent?nonce=...&dir=...` from the discovery file, or - when the daemon is down - calls `ensureDaemon()` and returns `''`. `ensureDaemon` launches the compiled `out/backend/daemon.js` **windowless/detached** via `spawn(process.execPath, [daemonJs], { detached:true, windowsHide:true, stdio:'ignore', env:{ ...process.env, ELECTRON_RUN_AS_NODE:'1' } })` + `child.unref()` (Electron-as-Node, so no separate Node install needed; the daemon is native-dep-free); it's guarded by an `isDaemonUp` port probe plus a 5s debounce, and the daemon's own single-instance guard makes concurrent launches safe. So opening a panel with no daemon spawns one and the overlay's retry loop (`needWsUrl`) connects once it's listening - no manual `start-argus-daemon.bat` needed (that and `yarn daemon` remain as manual/dev options). The daemon still self-exits ~10 min after the last panel closes. When `chat.html` has no URL it shows a **"Argus daemon not running"** overlay (`#daemon-down`, with a Retry button and the launch hint) and asks the extension for one via a `needWsUrl` message; the extension replies with a `wsUrl` message (the webview CSP blocks HTTP, so only the extension can re-resolve the nonce). **Daemon-restart recovery (nonce refresh)**: on WS close the bridge backs off then re-requests the URL (`requestWsUrl`) rather than reconnecting the stale baked URL, so a restarted daemon's new port/nonce is picked up; `applyWsUrl('')` keeps the overlay up and retries. The dev path (`server/index.ts` + `webview/index.html`'s `/nonce` XHR) is unchanged and not idle-killed. **A daemon is spawned from the install directory of whichever panel first needed it** (`ensureDaemon(extensionPath)`), so the process serving every panel may come from the repo's `out/` (Extension Development Host), or from any `~/.vscode/extensions/local.argus-<version>/` still installed - old installs accumulate and can win the respawn race, which is what the Info tab's `(stale)` Server row detects. Rebuilding this repo does not affect a daemon launched from an installed folder; restart it (`yarn daemon:stop`, then touch a panel) and confirm the `version` in `~/.Codex/argus-daemon.json`. See [!notes/common/backend-restart.md](!notes/common/backend-restart.md) for the full restart procedure, what needs `yarn build` vs `yarn compile`, and the detached target-first swap script (`!notes/common/scripts/restart-daemon-detached.js`) for restarting from **inside** an Argus conversation - the answering CLI is a child of the daemon, so a direct `daemon-stop` aborts the requesting turn, and plain kill-then-start loses the respawn race to any still-open old-install window

- **Daemon liveness is the port, never the pid.** Every "is a daemon there / may I discard this discovery file / may I kill this process" decision goes through `probeDaemon(port)` in `daemonInfo.ts`, which calls the loopback-only `GET /health` (it returns `{configPath, pid}`, so a valid answer proves something is listening, that it is an Argus server, and which process it is). The pid is used only as a cheap negative - a dead pid is conclusive, a live one proves nothing. **The pid check cannot be repaired by tightening it**, which is the trap `3bcfc37` ("Fix Windows PID recycling in daemon guard") fell into: `isProcessAlive` verifies the recycled pid belongs to `node.exe` or `Code.exe`, but the extension launches the daemon via `ELECTRON_RUN_AS_NODE` from `process.execPath`, so the real daemon **is** a `Code.exe` (`Code.exe …\local.argus-0.0.102\out\backend\daemon.js`) and that name must stay allowed, while a VS Code install runs dozens of other `Code.exe` utility processes for a recycled pid to land on. Measured: a discovery file's pid recycled **15h20m** after the daemon died, onto `Code.exe --type=utility --utility-sub-type=node.mojom.NodeService`. **The failure was permanent, not transient**, because three readers formed a closed loop with no exit - `ensureDaemon()` read "already running" and never spawned, `ChatPanel.buildWsUrl()` only called it in the `!info` branch so nothing ever revisited the conclusion (every reconnect rebuilt the same dead URL), and `verifyDaemonUp()`, the one place that already did a real port check, runs 4s **after a spawn** that never happened. The panel sat on Server `-` across VS Code restarts. So `buildWsUrl()` now fires `void ensureDaemon()` on **every** call, and `ensureDaemon` clears a file that points at nothing reachable (ownership-aware, `clearDaemonInfo(info.pid)`) before spawning. `probeDaemon` has three outcomes and the third is the safety valve: a timeout is **`busy`, deliberately not `down`**, because the daemon is single-threaded and a long synchronous stretch (a large transcript read, an `execFileSync` in the kill path) stalls its HTTP handler - calling that dead would discard the file of a daemon that still owns the port, whose replacement then exits on `EADDRINUSE`, leaving no file and no nonce, a permanent strand *worse* than the bug being fixed. Only a refused connection, or an answer that is not our JSON (a stranger squatting the port), counts as dead. The same rule applies to anything that **kills**: `restartDaemon()` confirms the pid is really our daemon before `taskkill /F /T` (on a recycled pid that tree-kill would have taken down part of the editor), and `scripts/daemon-stop.js` kills the pid the **port** reports rather than the one the file claims - it previously had no check at all and would have run `process.kill()` on a VS Code process while printing `[argus-daemon] stopped`. e2e: `e2e/daemon-liveness.spec.ts` (mock, on the compiled bundle; the decisive test asserts `isProcessAlive(pid) === true` **and** `isDaemonUp === false` on the same pid, so a pid-only build fails it, with a real `/health` and the stalled-server `busy` case as the controls). See [!notes/tasks/stale-daemon-pid/notes.md](!notes/tasks/stale-daemon-pid/notes.md)

- **The daemon re-asserts its own discovery file; losing it must not be terminal.** The file used to be written once, at startup, which made a deletion permanent rather than awkward: the extension reads no file and spawns a replacement, the replacement dies on `EADDRINUSE` against the incumbent that still holds the port, and the nonce needed to reach the incumbent exists **only in its memory** (`/health` returns `{configPath, pid}` and deliberately nothing else). Reported 2026-09-27 as a panel stuck on "Starting Argus daemon..." with the "failed to start automatically" toast, while pid 17368 sat on port 37071 answering `/health` perfectly, across VS Code restarts. This is precisely the strand the `busy` verdict above exists to prevent, arrived at from the other side: **that guard covers the path where the probe decides, and deleting the file does not free the port**, so any other deleter reproduces it. So `daemon.ts` keeps its startup registration in `registration` and `healRegistration()` re-writes it every `REGISTRATION_HEAL_MS` (10s; `ARGUS_DAEMON_HEAL_MS` overrides it for e2e) on an `unref`'d interval, which never holds the process past its idle shutdown. It rewrites **only when the file is missing or unreadable** - a file naming a different pid means another daemon registered itself, and overwriting that strands *it* identically, so we are the redundant process there, not the authority; `handingOff`/`shuttingDown` are excluded for the same reason. The nonce and pid are re-written **unchanged**, since a fresh nonce would lock out every already-connected client as thoroughly as the missing file did. Three deleters were hardened in the same pass, and the rule they now share is *never remove the registration of a daemon that is still alive*: `scripts/daemon-stop.js` ended in an unconditional `unlinkSync` reached even when the kill threw, and its own probe resolved a timeout to "not serving" rather than `busy` (it now leaves a busy port entirely alone and exits 1, and **verifies** a kill with `waitGone` before removing the file); `restartDaemon()`'s `clearDaemonInfo()` was not ownership-aware; and the `EADDRINUSE` message told the user to kill the holder, which for one of our own daemons means killing a healthy server whose registration is about to return, so it now probes the port and says which case it is. Residual: the heal bounds the outage at `REGISTRATION_HEAL_MS` rather than removing it, and a file naming a *dead* daemon while a live one holds the config port is still a strand, since the heal declines to touch a file that parses. e2e: `e2e/daemon-registration-heal-integration.spec.ts` (a deleted file comes back with the same port/nonce/pid, and a launch afterwards exits 0 instead of dying on `EADDRINUSE`, which is the reported failure stated as a property; the control is that a file naming another daemon is left untouched, without which a build that rewrote on every tick would pass both) and `e2e/daemon-stop-safety.spec.ts` (mock: a stalled daemon keeps its file, with a genuinely stale file still cleaned up and a live daemon still stopped as the two controls, so "never delete anything" cannot pass). See [!notes/tasks/daemon-registration-lost/notes.md](!notes/tasks/daemon-registration-lost/notes.md)

Usage bars come **primarily** from the live Anthropic usage API: `fetchUsage(force?)` reads the OAuth `accessToken` from `~/.Codex/.credentials.json` (runtime read, never logged/persisted) and `GET`s `https://api.anthropic.com/api/oauth/usage` with `anthropic-beta: oauth-2025-04-20` (60s `usageCache`, bypassed when `force` is true); `parseUsageResponse()` parses the response's `limits` array first (`parseLimitsArray`: kind `session` -> five_hour, `weekly_all` -> seven_day, `weekly_scoped` -> `seven_day_<model>` with a server-side `label` like "Weekly Fable" - model-scoped windows exist **only** in `limits`, the legacy keys never gain new families; unknown kinds skipped) and falls back to the legacy top-level known-window keys (`KNOWN_USAGE_WINDOWS`: five_hour/seven_day/seven_day_opus/seven_day_sonnet, each `{ utilization: <percent 0-100>, resets_at: <ISO|null> }`), normalizing utilization to 0..1 and resets to unix seconds. The rejection it was hiding is worth knowing generally: **`execFile` throws synchronously when the OS refuses a new process** (`spawn UNKNOWN`, errno -4094), a different path from the callback's `err`, and a throw inside a promise executor rejects it - so `fetchAccountInfo` could reject despite documenting that it always resolves, and is now wrapped in `try/catch` the same way `handleSend` guards `spawn()`. See [!notes/common/request-reply-invariant.md](!notes/common/request-reply-invariant.md). `fetchUsage(force)` returns `UsageResult { windows, error? }` where `error` is a short reason ("rate limited (HTTP 429)", "token expired (HTTP 401)", "request timed out", etc.); `rateLimits` uses API windows if non-empty, else accumulated stream windows; `usageError` is forwarded only when `rateLimits` is empty (no fallback to show). - Header usage indicator + central usage polling: the header (`topRightActions`, left of the Account & usage button) shows the current rate-limit windows as three stacked mini bars (`UsageIndicator`, `data-testid="usage-indicator"`, one `[data-window]` track per window carrying `data-percent`), clicking opens the Account & Usage modal. Labels, display order, percentage rounding and colour tiers come from `webview/src/utils/usage.ts`, which the modal's full bars use too, so the compact and full renderings cannot drift; at most three windows are shown (lowest `rateLimitOrder` first). **It replaced the separate "Account & usage" header button** (which did nothing but open the same modal), so it must stay clickable with no data: before the first poll lands, or while the usage API is rate-limiting, it renders that button's icon instead of bars (`.iconOnly`) - drawing three dead grey lines would look broken, and hiding the control would remove the entry point exactly when the user wants to open the panel and hit refresh. The slash menu's "Account & usage..." action remains the other way in, and is what every pre-existing e2e spec uses. **The webview never fetches usage for the indicator.** Exactly one poller runs per **server process** (never per client), started by `startUsagePoller()` in `src/backend/usagePoller.ts` from **`startServer()`** once it is listening - so the daemon and the dev server both have one, and the extension host (connect-only, no server) has none. It deliberately does not live in `daemon.ts`: with the dev server passive, the one-shot fallback fetch at connect was the only attempt, so a transient 429 left the bars blank until someone reloaded the page, which is exactly how the feature got reported as missing. Usage windows are machine-global, so a per-panel fetch would multiply requests against an endpoint that rate-limits hard (HTTP 429) while producing identical numbers. Polling is **activity-gated**, because the windows only move while tokens are being spent: `noteUsageActivity()` (called from `handleSend` for every send - including a mid-turn inject and a silent retry - and from `getAccountUsage {force:true}`, plus once at daemon startup) stamps a clock and, if polling was paused, resumes it with an **immediate** fetch; the interval then re-polls every `USAGE_POLL_INTERVAL_MS` (60s) and clears itself once `usagePollActive(lastActivityAt, now)` reports the `USAGE_ACTIVE_WINDOW_MS` (1h) window has closed, so a quiet machine makes zero requests until the next turn. `lastActivityAt === 0` ("nothing yet") is deliberately distinct from a stale stamp, so a daemon nobody uses never polls on a timer. A successful poll broadcasts `usageLimits {windows, fetchedAt}` via `broadcastToAllChannels()` (every client of every workspace); an unchanged window set broadcasts nothing. A client syncs on connect/reconnect with `getUsageLimits`, answered from `getUsageSnapshot()` when the poller has one, else from a single 60s-cached `fetchUsage()` (the poll may not have landed yet; it stays one request a minute however many clients ask). **`usagePoller.ts` is the only module that calls the usage API** (`session.ts` deliberately does not import `fetchUsage`, so the rate floor cannot be bypassed by a client-triggered handler). A client never fetches: opening the Account & Usage modal or clicking its refresh sends `getAccountUsage`, which calls `requestUsageRefresh()` - it answers from the snapshot when the last **attempt** is younger than `USAGE_MIN_REFRESH_MS` (60s), joins a request already in flight, or spends the one request this process is allowed, then broadcasts what it gets. So N panels hammering refresh cost at most one request a minute in total, and one person's refresh updates everyone's indicator. The floor is measured from the last *attempt*, not the last success: during a 429 a per-click retry would deepen the very limit the user is waiting out. `getUsageLimits`'s empty-snapshot fallback goes through the same call, so a reconnect storm cannot flood it either. `App.tsx` also adopts `accountUsage.rateLimits` locally (instant, and still works against an older daemon that predates the broadcast), and the modal adopts `usageLimits` pushes so it cannot freeze at its opening values while the poller ticks. **An empty payload never clears anything** - not the server snapshot, not the modal's bars, not the header's - it only records the reason; a reconnect landing on a 429 would otherwise blank a healthy indicator. The reply is sent **even when the fetch failed** (empty `windows` + a string `error`), so one request always yields one reply, a client can tell "unavailable" from "still loading", and the indicator's fallback tooltip can name the reason. A failed poll keeps the previous snapshot (a 429 is transient; stale-by-a-minute beats blank), and the snapshot is memory-only - after a daemon restart the indicator is blank for a few seconds rather than showing a percentage that may have moved. `ARGUS_USAGE_POLL=0` disables polling; it is set for e2e daemons (`startDaemon({usagePoll: true})` opts back in) **and in `playwright.config.ts`'s `webServer.env`** - a suite that reconnects hundreds of times would otherwise keep the dev server calling the live API on a timer, which rate-limits the account and then makes every API-dependent spec skip. `getUsageLimits` is in `webview/index.html`'s MOCK_SUPPRESSED so mock tests own the data. e2e: `e2e/usage-indicator.spec.ts` (mock) and `e2e/usage-indicator-integration.spec.ts` (integration, incl. a daemon that serves data older than the request plus a polling-disabled control)

- Model picker and model data: the Account modal "Models" tab and the InputArea quick picker list models from `getModels` -> `modelList {models: [{id, displayName, description?}], runtimeDefaultModel, error?}`. The server (`session.ts`) resolves each `description` via `describeModel()` in `src/backend/modelData.ts`: config-extracted per-family strings (`modelFamilyDescriptions`) first, then baked-in `FAMILY_DESCRIPTIONS` - descriptions are keyed by **family** (fable/opus/sonnet/haiku substring, mirroring the CLI's own classifier), never by exact id, so new snapshots never render blank. On a successful fetch the list is persisted to `modelListCache` in argus.json; a failed fetch falls back to that cache before the webview's tiny hardcoded trio. The webview keeps its own family fallback in `webview/src/utils/model.ts` (shared by both components: `describeModel`, `FALLBACK_MODELS`, `makeDefaultEntry`, `sameModel`) for old-daemon skew. **Active-row matching uses `sameModel(a, b)`** which strips a trailing `-20\d{6}` snapshot date from both sides, so a dated API id highlights against its dateless alias. **Model/effort/thinking are config-global**: the switch handlers write argus.json and notify every client of every workspace channel via `broadcastToAllChannels()` (channel.ts, module-level); `getInfo` and CLI spawns re-derive the values from `readConfig()` at use time (`SessionState` keeps only `serverDefaultModel`, the ARGUS_MODEL/startServer fallback) - per-entry cached copies used to go stale whenever the switch happened in another workspace channel or another server process, leaving panels highlighting and spawning the old model. Both `getInfo` responders reply through `buildWorkspaceInfo()` (`src/backend/workspaceInfo.ts`) - the WS server (session.ts) and ChatPanel's VS_ONLY extension path, whose hand-built reply used to carry only `{path, version}`: the reducer merges model/effort/thinking only when present, so a reloaded extension panel showed "Default (CLI)"/high while the daemon spawned the configured model (e2e: `e2e/workspace-info-config-integration.spec.ts`). **Daily refresh**: `daemon.ts` calls `scheduleModelDataRefresh()` after binding - stamps `daemonLastStartAt` on every launch, then runs `refreshModelData()` when `shouldRefreshModelData()` opens **both** clocks, and re-checks hourly for long-running daemons. The gates are never the launch time (the daemon idle-exits/respawns many times a day): `modelDataUpdatedAt` must be older than 24h **and** `modelDataAttemptedAt` older than 1h. The two clocks exist because a failed fetch must not hide a stale context window: `applyRefreshResult` advances the attempt clock unconditionally but the success clock **only when `models.length > 0`**, so an expired token or an offline machine retries in an hour instead of a day, while the previously cached windows survive untouched. Without the attempt clock a permanently broken environment would be stale forever and therefore re-attempt on *every* daemon start, each attempt spawning a real CLI turn - which is why the earlier code stamped success unconditionally, trading a day of a possibly 5x-wrong percentage (200k fallback on a 1M model) for that protection; the refresh detects the CLI default model (minimal `--print` turn in tmpdir, so no project AGENTS.md/memory is loaded), extracts family descriptions from the installed CLI bundle (anchored `value:"X",label:"Y",description:"Z"` scans; fable found as the unknown string clustered after the haiku wording), and re-fetches `/v1/models`; `ARGUS_MODEL_REFRESH=0` disables it (set by e2e daemonHelpers so test daemons never spawn real CLI turns); manual trigger `yarn update-models` (needs `yarn compile`). e2e: `e2e/model-picker.spec.ts` (mock), the two-clock refresh gate in `e2e/model-data-refresh.spec.ts` (mock), cross-dir switchModel in `e2e/shared-channel-integration.spec.ts`, daemonLastStartAt in `e2e/daemon-lifecycle-integration.spec.ts`

- CLI spawn guard: `handleSend` wraps `spawn()` in a `try/catch`. `spawn()` throws **synchronously** when the OS refuses a new process (resource exhaustion -> `spawn UNKNOWN`, errno -4094), which is a different path from the async `proc.on('error')` handler; uncaught it propagates out of the WS message handler and kills the entire server process, dropping every other client's connection. The catch clears `currentProc`/`currentProcKey`, sets `cliDone`, logs, and broadcasts `error` + `done` so the failure stays scoped to that one turn

- CLI stdin error handler: `proc.stdin.on('error', ...)` in `attachProcHandlers` (`src/backend/cliHandler.ts`) prevents the server from crashing when the CLI process dies unexpectedly (e.g. Bun panic); without it, a `write EOF` error on stdin propagates as an unhandled event that kills the Node.js server and drops all WebSocket connections

- Process lifecycle - **detach before kill, everywhere**: `/clear` and `stop` both clear `currentProc`/`currentProcKey` *before* `killProc()`, and `attachProcHandlers` guards stdout, stderr accumulation and the entire `close` body with `detached()` (`s.currentProc !== proc`). Reason: `close` lands a beat after the kill, and until it does the dying process still reports `stdin.writable === true` and still counts as `isActiveProc`. Without the detach, a `/clear` surfaced the force-killed exit code as a spurious "Something went wrong" block, and a **send issued right after a stop was taken for a mid-turn inject** (`handleSend`'s first branch tests exactly `currentProc?.stdin?.writable && !cliDone`), wrote into a pipe nobody reads, and the pending `close` then ended the fresh turn with a bare `done` - a ~1s empty turn, only "sometimes" because it depends on landing inside that window. `handleStop` therefore also broadcasts `done` itself rather than relying on the close event (the old `s.userStopped` flag existed only for that and is gone). The `detached()` guard additionally stops a killed proc's buffered output and its `close` from mutating the next turn's state (it used to disarm the new turn's watchdog via `watchdog.state.active = false`). e2e: `e2e/clear-integration.spec.ts`, `e2e/stop-then-send-integration.spec.ts`

- **Stop interrupts the CLI, it does not kill it** - killing it poisons the conversation the model sees. A killed CLI leaves its transcript ending on a user message nobody answered, and the CLI repairs that shape on the next `--resume` by splicing a fake assistant turn into the history: model `<synthetic>`, zero tokens, text `No response requested.` (the bundle's `Dne` constant, spliced in `deserializeMessagesWithInterruptDetection`). That repair **is sent to the model** on every later turn - proven by resuming a session holding one and asking the model to quote its own prior messages, which came back `No response requested.` / `OK` with the phrase never in the prompt. Across all 1,710 transcripts on the machine there are 292 such placeholders and 4 turns where the *model itself* emitted the phrase as a real 7-token answer to a real question; all 4 are in sessions that already held placeholders, and **none** of the 142 sessions with four or fewer produced one. Argus cannot remove the repair (the CLI rebuilds the conversation from the `.jsonl` itself), and interrupting does **not** repair the transcript either - measured three ways, the dangling user record survives even a clean interrupt whose turn ends properly. What fixes it is that the splice only fires when the *last* message is a user message: `handleStop` calls `interruptProc()` (`src/backend/cli.ts`, writes `{type:'control_request',request:{subtype:'interrupt'}}` on the stdin the stream-json input format already carries) and **keeps the process**, so the next send reuses it with no `--resume`, its answer lands after the abandoned message, and the abandoned message is no longer last - permanently, not until the next resume. `s.stopping` is the cost of that: the interrupted turn is no longer detached, so it keeps emitting for a few more milliseconds and signs off with an `is_error` result. `handleCliEvent` swallows everything while `s.stopping` and clears the flag on that `result` (which also retires `s.stopKillTimer`, the `STOP_INTERRUPT_TIMEOUT_MS` = 5s fallback that kills a CLI which never acknowledges). Without that guard the trailing chunks would append to a message the UI already committed, the autonomous-turn recovery branch would read them as a background-task turn and raise a phantom `thinking_start`, and the result would surface a "stopped" error block. A send arriving **before** the acknowledgement deliberately falls back to the old kill-and-respawn via `abortPendingStop()` - a pending result handed to the next turn would end it milliseconds in, the empty-1s-turn failure in another costume - which is why `e2e/stop-then-send-integration.spec.ts` still asserts `Spawning Codex` for a same-tick stop+send. `/clear` calls `abortPendingStop()` too; `newSession` deliberately does not, since it moves the client to a fresh entry and leaves the old one to whoever is still in it. **`loadSession` also hides the placeholder** (`isSyntheticPlaceholder`, matching the official client's `case Dne: return null`) so a replay does not show a reply the user never got; that is cosmetic and does not touch what the model sees. Still open: a session stopped and then abandoned (panel closed, daemon restarted) ends on the dangling record, and its next cold resume splices exactly one. Full analysis, bundle offsets and the probes: [!notes/tasks/no-response-requested/notes.md](!notes/tasks/no-response-requested/notes.md); e2e: `e2e/stop-no-placeholder-integration.spec.ts` (verified red at `Expected 0, Received 1` by forcing `interruptProc` to return false)

- Remote-access authentication: a client whose **peer address is not on this machine** must sign in before it can obtain a nonce or open a WebSocket; loopback and the VS Code webview are exempt and entirely unchanged. The gate is `isLocalAddress(req.socket.remoteAddress)` and deliberately **not** the Origin header - `originAllowed()` treats an absent Origin as local, so before this a client that simply omitted the header connected from anywhere even with `allowNetworkAccess: false`, and `GET /nonce` handed the nonce to whoever asked (both measured: [!notes/tasks/remote-access-auth/scripts/probe-origin-gate.js](!notes/tasks/remote-access-auth/scripts/probe-origin-gate.js)). **No password configured means remote access is refused, not open** - the strict default, so the hole stays closed even if nobody sets one. Flow: `POST /login {user,password}` -> `{token}` (32 random bytes, in-memory), then `?auth=<token>` on both `GET /nonce` and the WS URL; static assets stay public so the login screen can render, which grants nothing on its own. A **cookie was rejected**: the dev page is served by Vite on another port, so it would drag in CORS-with-credentials, and a browser cannot set headers on a WS handshake anyway - the URL is the only channel that works for both hosts. `/login` requires `Content-Type: application/json` (forcing a preflight cross-origin) and returns the token in the body, so a cross-site POST can neither be made silently nor read the answer. `enforceAuth()` mirrors `enforceOrigins()`: after a password change or "sign out all" it closes every **remote** socket whose token no longer exists (4401) and leaves local ones alone. UI: `LoginScreen.tsx` replaces the whole app (there is no usable connection behind it to cover) and `SettingsModal`'s Network tab carries the set/change/remove form plus "Sign out all devices"; the login screen states that the password crosses plain HTTP, which is the honest limit - this stops casual access on a shared network, not someone capturing traffic. **`auth_required` is raised before React exists** (the shim's first connect runs while the bundle is still evaluating) and `setRequired` dedupes, so it fired once, to nobody, and never again - the remote page rendered the chat while the socket looped on 401 in the console. The app therefore reads `window.argusAuthRequired()` once on mount, the same shape as the deep-link replay deferring to `webviewReady`; this was invisible to every rendering assertion and only the hands-on browser pass caught it. `ARGUS_AUTH_FILE` overrides the credential path and is pinned in `playwright.config.ts` so a suite run can never read or write the real one. e2e: `e2e/remote-auth.spec.ts` (mock + the credential store on the compiled bundle) and `e2e/remote-auth-integration.spec.ts`; see [!notes/tasks/remote-access-auth/notes.md](!notes/tasks/remote-access-auth/notes.md)
