# Stop all Claude CLI processes button (Settings > Info)

Worked on `main` (no ticket). Added a machine-wide "kill all Claude Code CLI processes" button to the Settings > Info tab, as a UI equivalent of `cmd/kill-claude.bat`.

## Why

The user wanted an in-app way to force-stop every running Claude Code CLI process, instead of running the `kill-claude.bat` script separately.

## Changes made

- **`src/backend/cli.ts`** - new `killAllClaude()`. On Windows: counts matches via `tasklist /FI "IMAGENAME eq claude.exe" /FO CSV /NH` (CSV output is locale-independent - it echoes the literal image name - unlike taskkill's own human-readable success/error sentences, which are localized), then runs `taskkill /F /IM claude.exe`. POSIX fallback: `pgrep -x claude` + `pkill -x claude`. Returns `{ count, error? }`.
- **`src/backend/session.ts`** - new WS message `killAllClaude` -> `killAllClaudeResult {count, error?}`, handled inline next to `restartDaemon`. Not `VS_ONLY` (same as `getServerInfo`) since the actual OS call has to run wherever the backend (daemon or dev server) is, not in the extension host. Also resets `cliLaunchCount = 0` when `result.count > 0` - see Gotchas.
- **`webview/src/components/SettingsModal.tsx`** - "Stop all Claude CLI processes" button in the Info tab, below the existing rows. Two-click **arm/confirm**: first click only flips the label to "Click again to confirm" for 4s (`killArmTimer`, auto-reverts, sends nothing); only the second click within that window posts `killAllClaude`. Result renders as a line below the button. The modal itself now gets `useDialogGeometry(modalRef, { persistKey: 'settings', defaultWidth: 340 })` (previously no `defaultWidth` at all) - see Gotchas for why.
- **`webview/src/components/SettingsModal.module.css`** - `.dangerBtn` / `.dangerBtnArmed` / `.fieldHintError`.
- **`!notes/common/security.md`** - new "Process termination - machine-wide (killAllClaude)" section (enriched the existing security-audit doc rather than creating a new one, since it already had a directly-relevant "Process spawning" section on `killProc()`'s `execFileSync` pattern).
- **CLAUDE.md** - both webview message protocol lines, the SettingsModal bullet, and the e2e file table.

## Tests

- `e2e/kill-all-claude.spec.ts` (mock, new): arm on first click + auto-revert without sending a message; result rendering (success/zero/error) via a simulated `killAllClaudeResult` reply.
- Full mock suite (174 tests) run to confirm no regressions from the SettingsModal changes.
- No integration test, and the real second click is not automated anywhere - see Gotchas.

## Gotchas

- **"CLI launches" stayed on the stale number after a real kill - because refetching alone wasn't enough.** The user reported the row still showed the pre-kill count after actually clicking through the button twice in their own running app. First fix: have `SettingsModal` re-`postMessage({ type: 'getServerInfo' })` right after receiving `killAllClaudeResult`, since the existing snapshot is only refreshed on mount/tab-switch/reconnect, never after this new action. That was real and necessary (confirmed via a live console log against the user's own dev server: each `killAllClaudeResult` now visibly triggers a new `getServerInfo` frame, and a simulated `serverInfo` reply with a different count did update the DOM) - but the user then reported the count *still* didn't change on the real button. The missing piece: `cliLaunchCount` is a monotonic spawn counter (`cliLaunchCount++` only in `handleSend`'s non-reuse branch) - killing a process is not a spawn, so the value itself never moves, and no amount of re-fetching a value that hasn't changed will show a different number. Fix: reset `cliLaunchCount = 0` server-side in the `killAllClaude` handler whenever something was actually killed (`result.count > 0`), so there is now something new for the refetch to pick up. **Both fixes were needed** - the refetch without the reset would keep showing the same (correct but stale-looking) old value forever; the reset without the refetch wouldn't reach the UI until the next incidental trigger (tab switch, reconnect).
- **The reset itself could not be safely live-tested end-to-end.** `killAllClaude()`'s OS-level side effect (`taskkill /F /IM claude.exe`) is machine-wide regardless of which server instance or session triggers it - there is no way to spin up an "isolated" test server that makes the real second click safe on this machine, since the real `claude.exe` behind this very agent session would still be a kill target. Verified the reset logic by code review only (a single `if (result.count > 0) cliLaunchCount = 0;`, synchronous, no race with the reply send) plus confirming the dev server's file-watcher (`scripts/dev.js` watches `src/backend/`) actually restarted and picked up the change (different PIDs on :3001/:5173 before/after the edit) - the actual "click for real, see it reset" confirmation had to come from the user.
- **The hint text's long sentence forced the whole modal wider - and the first fix (hardcoded `<br />` breaks) overcorrected.** SettingsModal had no `defaultWidth`, so it shrink-to-fits its widest row via plain CSS auto-sizing (`min-width: 240px`, no `width`). The hint sentence ("Force-stops every Claude Code CLI process on this machine...") was the widest content by far, so it alone pushed the modal from its usual ~250px to ~570px. First attempt: hardcode `<br />` breaks in the hint text (matching the existing pattern the Network tab's "Allowed origins" hint already uses) - this fixed the width, but only by accident of there being nothing else wide enough to matter yet. Once a real session existed with a real Transcript path (`C:\Users\...\<uuid>.jsonl`, ~90+ chars), *that* row forced the modal wide instead - and the hardcoded-`<br/>` hint stayed locked at its narrow 4-line wrap, now sitting oddly narrow inside a much wider modal. CSS can't have it both ways with `max-width` alone: a value that caps the hint's contribution to the ancestor's shrink-to-fit calculation also caps its actual rendered width, so it can never reflow wider later no matter how wide the container becomes. The only real fix is to stop the modal's width from being content-derived at all - give it a `defaultWidth` (as other centered modals here already do, e.g. Session History's 440) - so every row, including the hint (via normal wrapping) and the Transcript path (via its existing `.infoValue` `word-break: break-all`), reflows within one predictable width, including after a manual drag-resize.
- **This machine runs a real `claude.exe` that IS the agent session doing the work.** `tasklist` during this task confirmed exactly one `claude.exe` (PID 21268) running, presumably the CLI process behind the very Claude Code conversation implementing this feature. That makes the real "second click" send path (and any test that performs it) genuinely dangerous to exercise on a dev machine: it doesn't just affect Argus, it can kill the agent mid-task. Verified the OS-level logic (tasklist CSV counting + taskkill) safely instead, by pointing the same commands at a throwaway `notepad++.exe` process rather than `claude.exe`.
- **`killAllClaude` is not suppressed by the e2e mock harness.** `webview/index.html`'s dev-mode `MOCK_SUPPRESSED` list (`getSkills`, `listSessions`) exists to stop async replies from clobbering injected mock data - it has nothing to do with dangerous actions, and `killAllClaude` was never added to it. A mock e2e test that performs the real second click would still reach the live dev backend and run the real `taskkill`. `e2e/kill-all-claude.spec.ts` deliberately only clicks once (arms, sends nothing) and simulates the reply via `window.dispatchEvent` for the result-rendering assertions.
- **CSS specificity bug on the confirm state, caught by actually clicking it in a browser.** `.dangerBtnArmed { background: var(--error-fg); }` (specificity 0,1,0) lost to `.dangerBtn:hover { background: var(--diff-removed-bg); }` (0,2,0) whenever the mouse was actually hovering the button - which is the normal case right after the arming click, since the cursor is still sitting there. Result: the "Click again to confirm" text was a washed-out, low-contrast red-on-red. Fixed by giving `.dangerBtnArmed:hover` its own `background` declaration (same 0,2,0 specificity, wins on source order). This would not have been caught by reading the CSS alone - had to click the real button and screenshot it. Confirmed the fix by reading `getComputedStyle` immediately after a synthetic click (a real Playwright click plus a slow screenshot round-trip let the 4s arm timer expire before the check ran, which looked like a different bug at first).
- **`C:` drive was at 0 bytes free**, unrelated to this task - broke the first `yarn install` (no `node_modules` existed yet in this checkout) with `ENOSPC`. Not a project bug; see [common/development.md](../../common/development.md) for the workaround (this is why it's linked here, not repeated).
- **`package.json`'s version changed from `0.0.79` to `0.0.80` on disk partway through this session**, with no action from this session (`yarn compile` re-run confirmed it doesn't auto-bump). Most likely a concurrent edit from elsewhere (the `/bump` slash command is manual/user-triggered only, per `.claude/commands/bump.md`). Left untouched rather than reverted - not confirmed to be a mistake, and reverting someone else's possibly-intentional edit is riskier than leaving it.

## Decisions

- **Two-click arm/confirm on the client, not a `confirm()` dialog or a server-side "are you sure" round-trip.** No existing modal in this codebase uses `window.confirm()` or a second network round-trip for destructive actions (Session History's delete button fires on one click); a bespoke confirm dialog would have been a new UI pattern for one button. The arm/confirm state machine reuses the existing "click state persists briefly, then reverts" idiom already used for `SettingsModal`'s "Reset layout" flash feedback, just inverted (arm-then-fire instead of fire-then-flash).
- **No additional server-side authorization for `killAllClaude`.** Documented explicitly in `!notes/common/security.md`: any client that can open a WS connection here (nonce + Origin already checked at upgrade) can already do arbitrarily more damage via `send`/tool calls, so gating this one action further would not raise the real privilege boundary - only client-side misclick protection is warranted, which is what the two-click UI provides.
- **Counting via `tasklist ... /FO CSV /NH` instead of parsing `taskkill`'s own stdout.** `taskkill`'s human-readable "SUCCESS: ..." / "ERROR: ... not found." messages are localized to the OS UI language; the CSV image-name column is not. Counting first (before killing) also sidesteps needing to parse taskkill's output at all - the count comes from the pre-check, and taskkill's job is reduced to "did it throw or not."
