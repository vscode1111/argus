# UI and test conventions

Detailed conventions moved from `AGENTS.md`. Verify implementation details against current code before relying on a historical example.

- Model: agent model is free-text (`argus.model`); empty/unset defers to the Codex CLI default. Inline completions default to `Codex-haiku-4-5` (fast/cheap tier required)

- Streaming: always use `client.messages.stream()` + `finalMessage()`

- Tool approval: destructive tools (write_file, bash) require user confirmation via `showWarningMessage`

- No Python scripts - use Node.js/TypeScript for any tooling

- Webview UI is React 18 + TypeScript + Vite (lib/IIFE mode). Build with `yarn build`

- Webview styling uses CSS Modules (co-located `.module.css` files) with VS Code CSS variables (`var(--vscode-*)`) - no Tailwind, auto-adapts to any theme

- CSS Modules: camelCase class names for dot access (`styles.toolCall`), conditional classes via `.filter(Boolean).join(' ')`, shared modules in `components/shared/`, `composes:` for reuse

- CSS color tokens: diff/semantic colors defined as CSS variables in `global.css` (`--diff-added`, `--diff-removed`, `--user-msg-bg`, etc.) - never hardcode color literals in component CSS. **The unfilled part of any progress bar uses `--track-bg`, never `--input-bg`**: `--input-bg` is `--vscode-input-background`, which in some themes (Dark 2026, the one in `webview/index.html`) resolves to the *exact same colour* as the surface behind it, so the track disappeared and a 14% bar read as a floating stub with no sense of the full width. `--track-bg` is a `color-mix` wash of `--fg`, which contrasts by construction on any theme. Equal-colour bugs survive every layout assertion, so `e2e/usage-indicator.spec.ts` compares the computed track colour against its surface (verified red by reverting the token)

- Webview markdown rendered via `react-markdown` in `utils/markdown.tsx`

- Webview message protocol (extension -> webview): typed as `WebviewMessage` union in `ChatPanel.ts` - `thinking_start | thinking_chunk | text_chunk | tool_start | tool_end | done | error | message | clear | prefill | skills | workspaceInfo | log | clearLogs | loginUrl | loginResult | contextUsage | token_update | filePreview | retry_status | retry_clean | copyImageResult | user_inject | accountUsage | sessionList | sessionLoaded | workspaceList | allSessionList | dirList | clientCount | serverInfo | daemonRestarting | daemonStopping | sessionId | killAllClaudeResult | usageInsights | activeSessions | usageLimits | toolImage | fileList | bgTasks | bg_notice | cliProcessList | cliProcessKilled | clientList | clientClosed | authStatus | authResult | auth_required | panelVisible`

- Webview message protocol (webview -> extension): `send | stop | forceError | newSession | openFile | openUrl | getInfo | getSkills | retry | toolAnswer | login | loginCode | focusPanel | readFilePreview | copyImage | getAccountUsage | listSessions | resumeSession | deleteSession | renameSession | listWorkspaces | listAllSessions | switchWorkspace | listDir | getClientCount | getServerInfo | restartDaemon | stopDaemon | killAllClaude | getUsageInsights | getActiveSessions | getUsageLimits | readToolImage | searchFiles | getBgTasks | listCliProcesses | killCliProcess | listClients | closeClient | getAuthStatus | setAuthPassword | clearAuthPassword | signOutAll`

- Modal Escape handling: use `useEscapeKey(onClose)` hook from `hooks/useEscapeKey.ts` - do not duplicate keydown listeners

- Dialog state persistence: each centered modal (Session History, Workspace History, Account & Usage, Settings) remembers its **position, size, and selected tab**, persisted to `localStorage` so it survives a full page refresh. Backed by `utils/dialogState.ts` (a single `localStorage` key `argus.dialogState` holding a `Record<key, {pos,size,tab}>`, read/written per call via `getDialogState`/`patchDialogState`; storage errors are swallowed so geometry is best-effort). `clearDialogState()` removes that key (used by the Settings "Reset layout" button). Position/size are wired through `hooks/useDialogGeometry.ts` (replaces the old `useDraggable`): pass a `persistKey` (`Modal` forwards it; `SettingsModal` calls the hook directly). The hook applies width/height **imperatively** on the element (not via React's controlled `style`, which only carries the drag position) so the native CSS `resize: both` grabber keeps working; size is recorded **only** when the user actually drags that grabber (a `pointerdown` landing in the bottom-right ~18px zone, committed on `pointerup`), never on content-driven size changes - so a content-height modal (e.g. Settings) does not silently persist a size the user never set just from switching tabs; drag end records position. On mount, size is restored from the store or falls back to `defaultWidth`/`fullHeight`. The hook also returns `reset()`, which clears the live element's inline width/height and recenters it (`setPos(null)`) so a "Reset layout" click snaps the open modal back without a reopen. Tab persistence lives in each modal: `tab` initializes from `getDialogState(key)?.tab` and a `setTab` wrapper calls `patchDialogState`; Session/Workspace re-trigger their lazy tab loads (`listAllSessions` / `browseTo`) on mount when the restored tab is the lazy one. SettingsModal keeps its **tab** in `localStorage` (`argus.settingsTab`) and only adds geometry to the store. SettingsModal's footer has a bottom-right **"Reset layout"** button (`.resetCorner`, mirrors the bottom-left `dev` button) that calls `clearDialogState()`, removes `argus.settingsTab`, and `drag.reset()`s the open modal, then flashes "Layout reset" for 1.5s. e2e: `e2e/dialog-state.spec.ts` (mock, incl. persist-across-refresh + Reset layout) and `e2e/dialog-state-integration.spec.ts` (integration)

- Modal portals: FileViewerModal, DiffViewerModal, and ImageViewerModal use `createPortal(jsx, document.body)` to render outside the React tree, avoiding z-index stacking issues when modals are opened from inside the scrollable MessageList during streaming

- Preview ownership (file / diff / image): the **open state must not live in the component that was clicked**. A tool block is rendered by `StreamingMessage` while its turn runs and by `ChatMessage` once the turn commits, so the clicked `ToolCall` is unmounted the instant the turn finishes - which closed the modal under the user's cursor mid-read (the portal only fixes stacking, not lifetime; a `FilePathLink` inside streaming markdown had the same problem, plus constant re-rendering). `webview/src/contexts/PreviewContext.tsx` hoists it: `PreviewProvider` sits **above** `AppInner` in `App.tsx` and owns a stack of `PreviewRequest`s - `{kind:'file', path, content, line?, copyText?}`, `{kind:'diff', path, oldString, newString}` or `{kind:'diff', path, unifiedDiff}`, `{kind:'path', path, line?}` for "content not in hand", or `{kind:'toolImage', path, toolUseId}` for an image a tool returned. Consumers call `usePreview().open(req)`; nothing renders a preview modal itself except `AutoFileViewer` (the `?file=` launch param, already App-level). A `path` request is resolved by the host - it posts `readFilePreview`, matches the `filePreview` reply by exact path or `endsWith` (the backend answers with a resolved absolute path) and only then pushes the frame, so no empty modal flashes; this replaced two near-identical copies of that fetch in `ToolCall` (images) and `FilePathLink`. The state is a **stack**, not a slot, because previewed markdown linkifies paths too, so a path clicked inside a preview opens on top instead of replacing it; `onClose` at depth i truncates to i. `refresh(req)` replaces an open entry matched by `key` (`<toolCallId>:file` / `:diff`) and returns the **same array reference** when nothing matches, so the per-ToolCall effect that keeps a background Bash task's late output in sync doesn't re-render the provider on every result. Because `children` is a stable element, provider state changes never re-render the message list. The same rule applies to any state that must outlive a turn, not just previews: [!notes/common/state-lifetime-in-message-tree.md](!notes/common/state-lifetime-in-message-tree.md); e2e: `e2e/modal-persistence.spec.ts`

- **A tool's images never travel inside its result.** A Read of an image comes back as a base64 block, and those blocks were by far the largest thing Argus put on the wire: one real session held 48 of them, **23.4MB inside a 24.2MB `sessionLoaded` payload**, re-sent on every replay and reconnect (`ws` 8.20.0 defaults `perMessageDeflate` to false and `src/backend/index.ts` passes no override, so it crosses raw; base64 of JPEG barely deflates anyway). None of it was ever rendered - the preview re-read the file off disk, so an image the agent had since renamed, packaged or deleted opened as `Error reading file: ENOENT` while the bytes the model actually saw sat in the transcript. `stringifyToolResult()` (`src/backend/toolResult.ts`) therefore replaces every image block with `[image image/jpeg 174 KB]` on **both** paths that feed the webview - live (`cliHandler`'s `handleUserEvent` and `handleToolResult`) and replay (`sessions.loadSession`) - and the bytes are fetched one at a time, per click: `ToolCall` opens `{kind:'toolImage', toolUseId}`, `PreviewContext` posts `readToolImage {toolUseId, path}` and matches the `toolImage` reply **on the call id** (exact - the path-suffix match `filePreview` needs cannot tell two images in one turn apart), and `session.ts` answers from `readToolImage(channel.getViewingSessionId(ws) ?? s.sessionId, ...)`, the browsed session winning because that is the transcript on screen. It falls back to `readFilePreview(path)` only when the transcript has no image for that call (an old session, or a result line the CLI has not flushed yet), so the disk is the exception rather than the source. Measured on the reported session: **24.2MB -> 0.8MB**. Because the bytes now arrive per click rather than with the message, a content-less request (`path` **or** `toolImage`) **opens its modal immediately** and fills it in when the host answers: `open()` pushes a `Frame` with `loading: true` and a unique `loadId`, and the reply is written into *that* frame by id (`settle()`), so a second preview opened while the first is in flight cannot be overwritten by it. `FileViewerModal` takes a `loading` prop and renders `.loadingBody` + `.previewSpinner` (`data-testid="preview-loading"`) in place of the body, hiding the encoding select while there is nothing to decode; the header already shows the path, so the window says what it is fetching. Deferring the open until the content arrived (the first shape of this) left the click looking ignored for a second or more over a remote link. `PREVIEW_TIMEOUT_MS` (20s) closes the loop: the host answers even when the read failed (the error arrives as the content), so silence means a lost message or reply, and the frame settles to a "connection may have dropped" message rather than spinning forever. Same rule for anything large a tool can hand back: [!notes/common/large-tool-payloads.md](!notes/common/large-tool-payloads.md); e2e: `e2e/tool-image-preview.spec.ts` (mock) and `e2e/tool-image-preview-integration.spec.ts` (real CLI, the file deleted before the click)

- Errors use `showError()` helper in ChatPanel - shows VS Code error notification with "View Output" action

- AgentSession and ChatPanel use a shared `vscode.OutputChannel` ("Argus") for stderr and error logging

- Image paste: clipboard images are base64-encoded in the webview, sent via `--input-format stream-json` NDJSON to the Codex CLI with `type: "image"` content blocks

- Image copy: ImageViewerModal has a toolbar with copy and close buttons; copy button and Ctrl+C shortcut copy the displayed image to system clipboard; in VS Code extension mode, sends `copyImage` message with base64 data to ChatPanel, which writes a temp PNG and calls `copyImageToClipboard()` from `win32Clipboard.ts` (GDI+ loads the image, converts to CF_DIB + registered PNG format, sets both via Win32 clipboard API); in browser dev mode, `copyImageBrowser` converts data URLs to blobs via `dataUrlToBlob()` (base64 decode, no `fetch()` since Chromium blocks `fetch()` on data URLs), then writes via `navigator.clipboard.write()` with `ClipboardItem`; toast shows "Copied to clipboard" or "Failed to copy image"; `copyImage` is routed via VS_ONLY in `chat.html`; e2e tests in `e2e/image-copy.spec.ts`

- Slash commands: InputArea shows a dropdown when "/" is typed; sends `getSkills` to extension, receives `skills` response with `{ name, scope: 'builtin' | 'global' | 'project', description? }[]`; commands read from `~/.Codex/commands/` (global) and `<workspace>/.Codex/commands/` (project) as `.md` files with YAML frontmatter `description:` field; skills read from `~/.Codex/skills/` (global) and `<workspace>/.Codex/skills/` (project) via `SKILL.md` frontmatter; built-in commands hardcoded in `src/backend/index.ts`; `readCommandsDir` parses frontmatter for description, falls back to first non-frontmatter line; Tab or Enter selects highlighted skill; description truncated to 100 chars in dropdown; e2e tests in `e2e/slash-commands.spec.ts` (mock) and `e2e/slash-commands-integration.spec.ts` (integration)

- `@` file mentions and the picker: typing `@` opens a file explorer in `InputArea` (`data-testid="at-menu"`, rows `at-menu-item`, up row `at-menu-up`), reusing the slash menu's markup and styles. It exists because **a mention is not cosmetic**: the CLI expands `@path` in the mode Argus spawns it, but its parser stops at the first space, so `@Бискуб Константин Николаевич/…/Военный билет 12.jpg` was silently never attached and the model went hunting for a file it had been handed. `@"path with spaces"` is the only form that works (single quotes, `\ ` escaping and quoting outside the `@` all fail), so `mentionFor()` quotes a path that contains a space and leaves the common case bare - full findings in [!notes/common/at-mentions.md](!notes/common/at-mentions.md). `MENTION_RE` therefore accepts the quoted form (`/(?<=^|\s)@(?:"[^"\n]*"|\S+)/g`), which is **lexically unambiguous, so no host round trip is needed to decide where a mention ends**; three space-crossing regex rules were tried and killed first, the decisive case being `ping @snowy about the build see src/file.md`, which any of them swallows whole - do not retry one. Matching lives in **one** place, `findMentions()` in `filePath.tsx`, used by both the overlay and the sent bubble (two copies of the pattern is why the bug had to be found twice). UI rules worth keeping: the query **may contain spaces** (cutting it at the first one, as the slash trigger does, would defeat the whole point) and the menu closes on zero matches instead, which is what gets it out of the way when the `@` was ordinary prose; rows commit on **`onMouseDown`, not `onClick`**, because a click blurs the textarea first and the caret-relative `getAtContext()` then has nothing to replace; committing a **file** sets a one-shot `justCommitted` ref, since a complete mention under the caret matches itself and `setSelectionRange` fires a `select` event that reopened the menu on the thing just chosen; picking a **directory drills into it** rather than finishing (the mention is still written out in full, so the text is sendable at every step) and `getAtContext()` **strips quotes** from the query so the just-inserted folder becomes the next query; the dropdown's height is **measured** from `inputAreaRef.getBoundingClientRect().top` in a `useLayoutEffect`, not a `vh` fraction, because the input area is drag-resizable and also grows with pasted images; and the parent column needs **two** elements (outer `direction: rtl` for head-truncation, inner `<bdi>` to restore LTR - an RTL paragraph reorders the neutral edge characters, rendering `.vscode/` as `/vscode.`, and putting the isolate on the same element does not help since the class forces it RTL). No e2e specs yet

- Log panel: has its own settings dropdown (gear icon) with toggles for show time / show type; settings persisted via `SettingsContext` to localStorage (`argus.showLogTime`, `argus.showLogType`); log text is color-highlighted by content: "Spawning Codex" entries render green (`textSpawn`), "exited with code" entries render orange (`textExit`)

- Error handling: errors classified into `ErrorKind` (`auth | not_found | session | generic`) via `classifyError()` in `src/backend/index.ts`; webview shows structured error blocks with contextual actions (Login, Retry, New session); API errors delivered as text content (e.g. "API Error: 403") are detected via a 3-second stale timer in the server and converted to error+done events; if `error` arrives after `done`, the reducer retroactively marks the last assistant message's outcome as `'error'`

- Login flow: `AgentSession.startLogin()` spawns `Codex auth login`, captures OAuth URL, accepts auth code via stdin; webview `LoginPanel` in `ChatMessage.tsx` manages the UI; `LoginState` tracks phases (`idle | starting | url | submitting | success | error`)

- Retry: server stores `lastMessage`; webview sends `retry` message; server sends `retry_clean` (reducer removes trailing error-role messages and re-marks error-outcome assistant messages as `retried` to preserve content history) then re-emits as `send` with `_silent: true` (no duplicate user message); `thinking_start` is always sent regardless of `_silent` so streaming state initializes; retried messages show a compact yellow timer with "reconnected Nx" text instead of the full error block; e2e tests in `e2e/retry-clean.spec.ts`

- Sound on complete: `playCompletionSound()` in `App.tsx` via AudioContext; toggled by `soundOnComplete` setting in `SettingsContext`; suppressed when user manually stops the session (`outcome === 'stopped'`)

- Notify on complete: fires when streaming finishes (if `notifyOnComplete` enabled in `SettingsContext`); notification title includes project name, body shows last user message; suppressed on manual stop. Delivery is environment-routed in `App.tsx` via `fireNotification(title, body)`: in the **browser** dev/app window (`location.protocol !== 'vscode-webview:'`) it uses the web `Notification` API directly (clicking focuses the window; requires `Notification.permission === 'granted'`, requested on first enable); in the **VS Code** webview (`vscode-webview:` protocol) the web Notification API cannot reach the OS, so it posts a `notify {title, body}` message (added to `VS_ONLY` in `chat.html`) that `ChatPanel.ts` turns into a notification: on **Windows** it fires a real OS toast via `showWindowsToast(title, body, log, focusUri)` (`win32Toast.ts`, in-process koffi FFI -> WinRT, shows in the Action Center even when VS Code isn't focused), where `focusUri` is `vscode://<getExtensionId()>/focus`; clicking the toast uses **protocol activation** (the toast XML carries `activationType='protocol' launch='<focusUri>'`), so the shell ShellExecutes the URI, VS Code comes to the foreground, and the `UriHandler` registered in `extension.ts` (`uri.path === '/focus'`) calls `ChatPanel.revealForActivation()` to focus the last-focused panel - this avoids a COM activator and the cross-thread WinRT `add_Activated` callback that koffi can't safely service. If `showWindowsToast` returns false (non-win32 or FFI failure) it falls back to `vscode.window.showInformationMessage(...)` with an "Open" action that reveals/focuses the panel via the cached HWND (`win32Focus.ts`). SettingsModal surfaces the browser permission state under the toggle (browser mode only; nothing shown in VS Code mode since it fires a real OS toast with no permission to manage): `granted` -> "allowed"; `denied` -> "Blocked in the browser..."; `default` -> "Grant permission" button

- Copy buttons: user messages have a hover-reveal copy button (`MessageCopyButton` in `ChatMessage.tsx`); code blocks have a hover-reveal copy button (`CopyButton` in `utils/markdown.tsx`) styled via `global.css` (`.code-block-wrapper` / `.code-copy-btn`). The code-block markup is deliberately **two** elements and must stay that way: a non-scrolling `div.code-block-wrapper` (`position: relative`, `width: fit-content`, `max-width: 100%`) wrapping the `pre` that carries the background, padding and `overflow-x: auto`. Merging them back (the `pre` being both scroll container and positioning context, as it was) breaks the button: an absolutely positioned child of a scroll container is anchored at scroll origin and then scrolls with the content, so it slid left out of view as soon as a long line was scrolled right. The button's background is opaque (`var(--tool-bg)`, was `transparent`) because it now sits permanently over scrolling code. Same rule for any future hover control over a scrollable region: [!notes/common/overlay-controls-on-scrollable.md](!notes/common/overlay-controls-on-scrollable.md); e2e: `e2e/code-copy-button.spec.ts`

- SettingsModal: fixed centered modal with 4 tabs (General, Watchdog, Network, Info); selected tab persisted to localStorage (`argus.settingsTab`); General tab has toggles for verbose tools, show timer, show output, show logs, sound/notify on complete; Watchdog tab has enabled toggle + NumberInput fields for timeout, auto retries, base delay, delay factor (disabled when watchdog off); Network tab has the `allowNetworkAccess` toggle ("Network access") plus a `TextInput` for `allowedOrigins` (comma-separated extra hosts, disabled when network access is off) - both write through `updateSettings` to `argus.json` and gate the WS Origin check (see Security hardening) - and an "Active connections" row showing the live count of open WS client sockets: SettingsModal sends `getClientCount` on mount and listens for `clientCount {count}` messages; the server (`src/backend/index.ts`) also **pushes** `clientCount` to all clients on every connect/disconnect (counting only `readyState===1` sockets via `broadcastClientCount`), so the number updates in real time; the count is wired through the `ConnectionHooks.getClientCount` passed into `handleConnection`; **the number is a button** (`.addrLink`, Enter/Space, like the Info tab CLI values) that opens `ClientsModal` - the count alone cannot say whether one of those connections is somebody else, which is the question that matters the moment Argus is reachable from off this machine; the Network tab also has two daemon settings as inline `settingRow` `NumberInput`s - **"Daemon port"** (bound to `daemonPort`) and **"Daemon idle timeout (min)"** (bound to `daemonIdleMs`, stored in `argus.json` as ms; the UI converts ms<->min via `daemonIdleMs/60000` and `min*60000`) - with a shared "Apply after a daemon restart" hint; both write through `updateSettings` like the others, but only the daemon reads them (the dev server uses a fixed `:3001` and has no idle), so they take effect on the next daemon restart. The **Daemon port** row also has a **randomize** button (`.randomBtn`, dice icon, to the left of the input inside a `.portControls` flex span) that fills a random non-popular port via the module-level `randomPort()` (draws 1024-65535, re-rolls if it hits the `POPULAR_PORTS` set of well-known/common dev ports like 22/80/443/3000/3001/3017/5173/8080/…); `NumberInput` syncs its prop to local text (`useEffect` on `value`) so the new value shows immediately. The field is **seeded from the actual running port**, not the stored config: a `useEffect` on `serverPort` (the live port from `serverInfo`) calls `setLocalDaemonPort(serverPort)` when they differ - **display state only, it does not write the config** (verified: with the field showing 3001 from a dev-server panel, `argus.json` still held its own `daemonPort`), so the shown value and the stored one can legitimately disagree and only an edit, randomize or Apply commits anything. The flip side is that in a **dev-server** panel the field shows `3001`, which is not a daemon port at all: editing or randomizing there writes `daemonPort` into the shared config, and the next real daemon start would then fight the dev server for that port, so on open the Daemon port input shows the port the daemon is really listening on (the configured `daemonPort` can be stale - set then never applied); randomize/Apply still override it. The live "HTTP/WebSocket address" rows (which show the actually-connected port) therefore now match the Daemon port field until the user changes it; an **"Apply (restart daemon)"** button below those fields posts `restartDaemon` to restart the daemon so the new port/idle take effect (it disconnects all clients + ends any running turn - tooltip warns). Restart is host-routed: in the **extension** `restartDaemon` is `VS_ONLY` so `ChatPanel` calls `restartDaemon(extensionPath)` (hard-kill the discovery pid, clear the file, force-spawn a fresh daemon) and the webview reconnects via the rewritten discovery file; in the **browser** it goes over WS to the daemon's in-process self-restart which broadcasts `daemonRestarting {port,url}`; the dev server has no `onRespawn` so it's a no-op there. The **"HTTP/WebSocket address"** values are clickable (`.addrLink`): HTTP opens the URL (`openUrl` postMessage + `window.open` in browser), WS copies to clipboard; both refresh after a reconnect because the modal re-sends `getServerInfo` on each `ws_status connected`. On a port-change restart a browser tab can't follow (it's same-origin to the old port), so on `daemonRestarting` with a different port it shows a **"Daemon moved... Reconnect at &lt;url&gt;"** clickable notice (`movedUrl`); Info tab shows **Client** (this extension/UI build, injected by `ChatPanel`) and **Server** (the version of the daemon actually serving the connection, from `serverInfo.serverVersion` -> `readServerVersion()` in `src/backend/version.ts`, which reads the `package.json` above the compiled output so a daemon launched from an installed extension folder reports *that* install's version); the two are separate installs joined by a machine-global discovery file, so either side can be the one left behind - an old daemon left running elsewhere serves a newer panel, or (equally common) the daemon gets rebuilt/restarted to a newer version while this panel's own build is unchanged; `compareVersions()` numerically orders the two `x.y.z` strings (a plain string compare gets `"0.0.9"` vs `"0.0.10"` backwards) so `<v> (stale)` in `.infoValueWarn`, with an explanatory tooltip, lands on whichever row (`clientIsStale` or `serverIsStale`) is actually behind rather than always the Server row (skew is only flagged when both sides are known). Also: workspace path, CLI launches, the live **Session** id and its **Transcript** path (both from `serverInfo`, which now carries `sessionId` plus `sessionPath` from `sessionFilePath()` in `sessions.ts`; the id is empty until the CLI reports one and the path is null until the project folder exists); the workspace path, session id, transcript path and WS address are click-to-copy via the shared `CopyableValue` component, which keeps the value in the layout and only hides it behind a "Copied!" badge (swapping the text outright collapsed the content-sized modal); `copiedKey` (not a shared boolean) scopes the feedback to the clicked row; all setting labels have `title` tooltips; `NumberInput` component uses local string state for editing UX, allows empty field while focused, falls back to `min` value on blur; `TextInput` component uses local string state and commits on blur/Enter; on mount, sends `getSettings` to re-fetch current server config (prevents stale cached values). The Info tab also has a **"Stop all Codex CLI processes"** button (`.dangerBtn`) below the info rows - a machine-wide kill switch equivalent to `cmd/kill-Codex.bat`'s `taskkill /F /IM Codex.exe`, not scoped to this panel's own session (it can terminate an unrelated CLI session elsewhere on the box). Backed by `killAllClaude()` in `src/backend/cli.ts`: on Windows, counts matches via `tasklist /FI "IMAGENAME eq Codex.exe" /FO CSV /NH` (CSV so the count doesn't depend on taskkill's own localized success/error text) then runs `taskkill /F /IM Codex.exe`; POSIX fallback uses `pgrep -x Codex` + `pkill -x Codex`. Wired over the plain WS bridge (not `VS_ONLY`, same as `getServerInfo`) as `killAllClaude` -> `killAllClaudeResult {count, error?}`, handled in `session.ts` next to `restartDaemon`. Because this can also kill the CLI process behind the very turn that triggered it (or, on a dev machine, an unrelated `Codex.exe`), the button requires a two-click **arm/confirm**: the first click sends nothing, just flips the label to "Click again to confirm" (`.dangerBtnArmed`) for 4s (`killArmTimer`, auto-reverts); only the second click within that window posts `killAllClaude`. `.dangerBtnArmed` must redeclare `background` under its own `:hover` (not just `opacity`) - `.dangerBtn:hover`'s translucent wash has equal-or-higher specificity and otherwise wins while the cursor sits on the button, which is the common case right after the arming click, washing the confirm state out to low-contrast text. Result renders as a `fieldHint`/`fieldHintError` line below the button ("Stopped N processes." / "No Codex CLI processes were running." / "Failed to stop processes: &lt;error&gt;"). `cliLaunchCount` (see the "CLI launches" row above) only ever **increments** on spawn, so killing processes alone never moves it - a kill would otherwise look like a no-op on that row. `session.ts`'s `killAllClaude` handler resets `cliLaunchCount = 0` whenever `result.count > 0` (something was actually killed), and the modal re-fetches `getServerInfo` right after receiving `killAllClaudeResult` so the row picks up the reset immediately instead of waiting for the next tab switch or reconnect; the "CLI launches" tooltip spells out the reset ("...or since the last 'Stop all Codex CLI processes'"). e2e: `e2e/kill-all-Codex.spec.ts` (mock) covers the arm/auto-revert, result rendering, and that a `killAllClaudeResult` triggers a `getServerInfo` re-fetch (asserted via a `WebSocket.prototype.send` interception, since outgoing webview->server messages never surface on `window`'s own `'message'` event) - a real second click is never exercised in tests (`killAllClaude` is not in `webview/index.html`'s dev-mode `MOCK_SUPPRESSED` list, so it would reach the live backend and actually terminate every `Codex.exe` on whatever machine runs the suite). It is **share of one core** - 100% is one core fully busy, measured at 98.6% against a deliberate busy loop while the same process reads 4.1% in Task Manager on this 24-core box - so the column header's tooltip names both the convention and the core count. A pid whose recorded start time changes is treated as recycled and loses its baseline. Ownership: `listOwnedProcs()` (channel.ts) maps each entry's `currentProc.pid` to its session; on Windows that pid is the **cmd.exe shell** (`shell: IS_WIN`), so a Codex.exe counts as ours when its **ppid** is owned, and the session id comes from that map rather than the process's `--resume` argument, which a brand-new conversation does not have. **"Running" and "Last activity" have different sources, and neither can be derived from the other.** `sessionRunning` is `boolean | null` and comes **only** from the server's own registry (`listOwnedProcs` reports `currentProc && !cliDone`, the same test `listActiveSessions` uses): a foreign process is `null`, rendered `-`, never `no`, because nothing observable from outside separates a CLI waiting for input from one working. In normal use that is not a gap - the daemon serves every panel, so it owns every row; the `-` only shows up when a *dev server* panel looks at the daemon's CLIs. `lastActivityAt` is the transcript's mtime, resolved through `sessionLastActivity()` in `sessions.ts` for **any** session id including foreign ones (path cached per id, since the probe walks all ~488 project folders; a miss is re-probed after 30s because a new session has no file for its first seconds). **The mtime is deliberately not used as a liveness signal**: measured on a session that was actively mid-turn, the transcript went **0 writes in 10 seconds** (mtime aged 4.2s -> 29.9s), because the CLI writes at message boundaries, not continuously - so "recently written" would have reported a working session as idle. - Idle CLI reaper (Settings > Watchdog, "Idle CLI timeout (s)"): a finished turn deliberately keeps its CLI process so the next send can reuse it, which costs **~250MB resident per abandoned panel** for the life of the server - two idle CLIs on a dev server was what prompted this. `cliIdleTimeoutSec` in `argus.json` (**0 = off, the shipped default**, because terminating a process on a timer is the user's call and must not start happening silently on upgrade) makes `startServer` sweep every `CLI_REAP_SWEEP_MS` (60s) and call `reapIdleCliProcs()` (channel.ts, which owns the registry and already imports `killProc`). The config is re-read **on every sweep**, so a change applies within a minute with no restart (that sweep interval is also the limit's granularity: a CLI dies between the limit and the limit plus a minute), unlike the daemon port/idle fields. Scope is this server's own entries only - a foreign CLI is never touched, matching what the process modal can say about it. **It skips any entry that is mid-turn (`!cliDone`), and that is a correctness guard rather than politeness**: killing a CLI whose transcript ends on an unanswered user message makes the next `--resume` splice a synthetic "No response requested." assistant turn into the conversation, which the model then sees forever ([!notes/tasks/no-response-requested/notes.md](!notes/tasks/no-response-requested/notes.md)); an idle process has already answered, so its transcript ends on an assistant record and nothing is spliced. It detaches before killing (the "detach before kill, everywhere" rule) and **keeps `sessionId`**, so the next message respawns with `--resume` and the conversation continues - verified live end to end: a real idle CLI was reaped by the running server (9 processes -> 8, its row's "this server" badge gone), and the next send resumed the same session id and correctly recalled the pre-reap turn at 113k input tokens. Deliberately separate from the retry watchdog above it in the same tab (that one restarts a stalled *turn*; this one reclaims idle *processes*), which is why the label carries an `.infoScope` qualifier - the same fix the CLI launches/processes pair needed. A longer explanatory hint under the field was tried and **removed at the user's request**: the qualifier plus the label tooltip already carry it, and a paragraph of prose in a settings list is noise. e2e: `e2e/cli-idle-reaper.spec.ts`

- Idle connection timeout (Settings > Network, "Connection idle timeout (min)"): reported with a screenshot - 11 Connected Clients rows idle 1-7+ hours against only 2 live CLI processes. The existing ping/pong liveness check (`wsAlive` WeakMap, 15s `PING_INTERVAL`, `client.terminate()` on a missed pong) was ruled out as the explanation before writing any code: it already catches a genuinely dead socket within ~30s, so it was not the gap - these were real, connected, merely unused VS Code panels (other projects, unfocused windows), which only an idle-since-last-activity clock can catch. `connectionIdleTimeoutSec` in `argus.json` (**0 = off**, same "not something to start doing silently on upgrade" default as `cliIdleTimeoutSec`) mirrors the CLI reaper one layer up: `reapIdleClients()` (channel.ts) runs off the **same** sweep timer as `reapIdleCliProcs` (both now driven from one `setInterval` in `startServer`, reading `reapSweepMs()` - a function, not a module-level const, since a module-level `Number(process.env.ARGUS_REAP_SWEEP_MS) || 60_000` captured at import would silently ignore the override on a second in-process `startServer()` call in a reused test worker), skips an entry with zero clients (already on the ordinary 30s grace-eviction path) or one that is mid-turn, and closes every open client of a stale entry with **`CLOSE_CODE_IDLE` (4002)** - a second code alongside the Connected Clients disconnect button's 4001, so the two reasons stay distinguishable in logs and tests even though the client treats both as "do not blindly backoff-retry". **Unlike a manual disconnect, an idle-closed connection is meant to come back on its own** once the panel is looked at again, not only on a click - this was asked as a direct design question rather than decided unilaterally, since it is real new client-side surface, not a copy of the disconnect button's mechanism: `ws-bridge.js` tracks `stoppedReason: 'peer' | 'idle' | null` (was a plain `closedByPeer` boolean) and exposes `reconnectIfIdle()` alongside `reconnectNow()` - a no-op unless the reason is `'idle'`, so it can never resurrect a deliberate peer disconnect. The existing `visibilitychange` listener (the two browser-tab hosts) now also reconnects on an idle close, not only on an ordinary drop; the VS Code webview has no working `document.hidden` of its own (`retainContextWhenHidden: true` keeps the script running regardless of tab visibility), so `ChatPanel.ts`'s previously `lastFocused`-only `onDidChangeViewState` handler now also posts `{type: 'panelVisible'}` when `e.webviewPanel.visible` becomes true (`visible`, not `active` - a panel showing in an unfocused split view should still reconnect), and `chat.html` turns that into `bridge.reconnectIfIdle()`. The manual Reconnect pill (`InputArea.tsx`) still works for either reason (an explicit fallback), with reason-specific tooltip text so it does not claim a peer close will "reconnect automatically" or an idle one needs a click. **A correctness gap found while designing this, not in the original report**: each VS Code panel owns its session entry via a stable `?panel=<uuid>`, so closing an idle panel's last socket runs the *existing* 30s grace timer into a *full entry eviction* - which, unlike `reapIdleCliProcs`, discarded `sessionId` entirely. Since an idle-timeout reconnect is unlikely within 30 seconds by construction, every idle-closed panel would have silently lost the ability to `--resume`: the old transcript stays on screen (a WS reconnect never clears React state), but the next message sent would silently start a brand-new CLI conversation with no memory of it - and the identical gap already existed, lower-probability, for the pre-existing manual-disconnect button. Fixed with `ChannelData.ownerLastSession: Map<panelId, sessionId>`, written whenever an owned entry evicts (**synced, not only-if-present** - an entry with no sessionId at eviction, e.g. "New chat" clicked then abandoned, must *clear* a stale mapping too, or a much-later reconnect would silently resurrect a conversation the user had already left) and consulted in `addClient`'s panelId branch when no live entry matches, seeding the fresh entry's `sessionId` before the client joins - no history replay needed, since the client's own view of the old transcript is already on screen. `ClientChannelInfo`/`ClientInfo` gained `lastActivityAt` (the same clock the reaper reads), rendered as a new "Last activity" column in `ClientsModal` (740px -> 820px). e2e: `e2e/connection-idle-reaper.spec.ts` (mock - `reapIdleClients` decoy tests mirroring `cli-idle-reaper.spec.ts`, plus the `ownerLastSession` continuity tests; caught two flaky-test traps of its own, not product bugs - an env override set at file top-level and deleted in `afterAll` silently reverts under `--repeat-each`, since `beforeAll`/`afterAll` re-fire per repeat while top-level module code runs only once) and `e2e/connection-idle-timeout-integration.spec.ts` (a real daemon on a private port + isolated config, a real browser page, a `document.hidden` override, and a real second `ws` client for the peer-close control - the decisive test, since a build that resurrected *any* terminal close on visibility, not only an idle one, would otherwise pass the primary case too); see [!notes/tasks/connection-idle-timeout/notes.md](!notes/tasks/connection-idle-timeout/notes.md)

- File-path regex pair and the `!notes` convention: two regexes run in sequence over the same text and must be widened together - `WIN_PATH_RE` (`markdown.tsx`) escapes backslashes **before** the markdown parser eats them, `FILE_PATH_RE` (`filePath.tsx`) linkifies the parsed text; a class one accepts and the other rejects yields a half-linked path. Both allow `!` in **directory** segments (the `!notes/` convention: `D:\_Projects\CCS\!notes\tasks\x.md`) but not in the final filename class, so prose like `done!file.md` is not swallowed. **The filename suffix is `\.\w+(?:-\w+)*`, not `\.\w+`**, because a dotfile is routinely hyphenated (`.corp-account`, `.menu-cms`) and `\w` excludes `-`: the match used to stop mid-name, and the two regexes then failed *differently* on the same path - in a code span `C:\…\credentials\.corp-account` linkified as `C:\…\credentials\.corp` (a file that does not exist, so the click opened ENOENT), while in prose `WIN_PATH_RE` missed it entirely and markdown ate the backslashes around each dot (`C:\Users\Admin.Codex\…\credentials.corp-account`). The post-extension `(?:-…)*` group stays deliberately ASCII, which keeps a Russian suffix ("`.md`-файл") out of the link. The class before the dot is `*` on the unix and relative branches so the final segment may *start* with it (`/etc/.gitignore` never linked before); the Windows branch never had that gap since its class includes separators. **`@` is a filename character too, and is allowed asymmetrically**: anywhere on the Windows branch (the drive letter is the evidence and an address cannot follow one, which is what the mid-segment cases need - `garland@2x.png` retina assets, `browser@6e474dac…`), but on the unix and relative branches only inside a directory segment and at the *start* of the final one (`@?`), since that is where a scoped package name puts it while an address puts it in the middle, so `docs/john@corp.com` stays prose. Rejecting it produced not "no link" but a **wrong** one: `D:\_Projects\_tools\telegram\out\@snowy_137.json` fell back to the longest directory prefix `…\out\`, an existing folder, so the click opened a listing; `…\node_modules\@scope\…\x.ts` split into that folder plus an orphan `@scope/…` fragment; `/home/u/node_modules/@types/node/index.d.ts` fell through to the relative branch and lost its leading slash. The widening was audited by diffing HEAD-vs-worktree links across 1,471 real transcripts (60,653 blocks): 94 added, every one a filesystem path, zero handles and zero addresses. **In prose a mid-segment `@` is still lost, and not to the regex** - remark-gfm autolinks `garland@2x.png` as `mailto:` before the linkifier runs and splits the text node; escaping it as `\@` in `escapeWinPaths` does not stop micromark (measured, then reverted rather than left as dead code), code spans are unaffected, and the reported path is immune because a separator precedes its `@`. **A directory is a path too, and the extension requirement is dropped on the Windows branch only** - the drive letter is what identifies the text as a filesystem path, and nothing else does. Its tail is segments plus a final segment plus an optional separator, with two guards on that final segment: it may not end in a dot (so a sentence's full stop stays prose, and the elision `C:\...` is not a path) and may not be empty (so a bare `C:\` is not a link). Before this, a dotless final segment matched a **shorter prefix** rather than failing, so `C:\Users\Admin\.Codex\skills\git-remarks\scripts\` linked `C:\Users\Admin\.Codex` - a real but entirely different directory, which the previewer then opened as EISDIR. Widening the slash branches the same way was tried and **reverted**: a URL path in prose is shaped exactly like a directory, so rendering one real session produced links to `/api/probes/` (out of `GET /api/probes/headers`) and `/api/v4/projects/6829/merge_requests/99/discussions/` - a leading slash is not evidence of a filesystem, and a bare relative path has no evidence at all. `WIN_PATH_RE` widened in step but deliberately **more loosely** (its final segment stays optional), because the two regexes answer different questions: escaping asks "would markdown eat this backslash" (true of `C:\` and `C:\...`), linking asks "is this worth opening" (false for both), and over-escaping only makes a backslash visible while under-escaping corrupts the text. Note also that **changing what a link matches changes what gets requested** - the trailing separator broke the reply matcher, since the host resolves it away and `got.endsWith(wanted)` then rejected the answer to its own question, fixed via `matchesRequestedPath()`. `protectPathBackslashes()` splits code spans/fences out via `CODE_SPAN_RE` and escapes only the text between them - backslashes are already literal inside code, so escaping there renders a doubled `CCS\\!notes`. **A URL's path component matches `FILE_PATH_RE` exactly**, so `linkifyPaths()` matches `URL_RE` (`webview/src/utils/url.ts`, `scheme://…` up to whitespace) **first**, renders each hit as a `UrlLink`, and lets the path scan see only the spans between URLs - otherwise `https://192.168.0.12/ui/scripts/main.js` rendered with `/192.168.0.12/ui/scripts/main.js` underlined and opening a preview for a file that does not exist on this machine, and `http://localhost:3001/webview.js` broke mid-host into `3001/webview.js`. **"Not a file path" is not "not a link"**: the URL stays clickable and opens via `openExternal()` (`postMessage openUrl` -> `vscode.env.openExternal`, plus `window.open`; both fire unconditionally, matching the login link and the Account & Usage footer), and the click must `preventDefault()` because in browser mode a bare `href` navigates the Argus page away - `MarkdownLink` routes `http(s)` through the same helper for that reason. `.external-url-link` is deliberately styled as a plain hover-underline link, not with `.file-path-link`'s dotted underline, since the dotted style is the app's signal that a click stays inside Argus; `trimUrl()` keeps a trailing full stop out of the link. In prose remark-gfm already produces an `<a>` that `withLinkedPaths` skips, so the bug only showed where it does not reach: code spans, fenced blocks, and the plain-text body of a user message - the three places the regression spec covers, each pairing the URL with a real path in the same message so neither "nothing is linkified" nor "everything became one kind of link" can pass. **Non-ASCII segments and spaces both link now, and they had to be fixed together** - every path in the reporting workspace has both (`d:\_BiskubFamily\Docs\Бискуб Константин Николаевич\Военный билет\Военный билет 12.jpg`). `\w` is ASCII-only in JS, so a Cyrillic segment ended the match and, a directory being a valid target, it fell back to the longest ASCII prefix - `d:\_BiskubFamily\Docs\`, which **exists**, so the click opened a listing and nothing looked broken. Both regexes now carry the `u` flag and are **composed from shared parts exported by `filePath.tsx`** (`PATH_CH`, `PATH_SEG`, `PATH_FINAL`, `WIN_TAIL`) which `markdown.tsx` imports - inline they exceeded ~500 characters and were no longer reviewable, and sharing the parts is what stops the pair drifting. Spaces are allowed on the **Windows branch only**, with three guards a 78,551-block transcript audit forced: a segment may not **start** with a space (so `see d:\Docs\ and also x\y.md` stops at `d:\Docs\`); a **spaced segment may not contain a dot**, because the segment loop is greedy and otherwise ate prose whenever a separator turned up later (`…\tools\vault.js show companies/GMTrade/credentials/.linear` linked whole); and the **final** segment, which does need spaces (`…\Военный билет\Военный билет 12.jpg`), is anchored on an extension and crosses them **lazily**, so `file.md and see other.txt here` stops at `file.md` where a greedy scan runs to `other.txt`. The extension itself stays ASCII - widening it made Russian initials parse as one (`…\Согласие на дарение Бискуб Н.М` matched with `.М` as the extension). `WIN_TAIL` is `(?:(?:SEG[\\/])+(?:FINAL)?|FINAL)`: making the final segment simply optional linkifies a bare `C:\` and the elision `C:\...`, while requiring it truncated a spaced directory to `d:\Docs\Военный`. **The hand-written corpus was fully green and the audit still found two false-positive classes** neither the author nor the bait had imagined - that is what the corpus is for, not a formality. Residual and irreducible without the filesystem: a dot-free prose run followed by a separator (`D:/_Projects/_tools/telegram and check dist/`), 3 distinct cases in 78k blocks. See [!notes/common/markdown-file-paths.md](!notes/common/markdown-file-paths.md); e2e in `e2e/file-path-bang-folder.spec.ts`, `e2e/file-path-at-sign.spec.ts` and `e2e/url-not-file-path.spec.ts`

- Security hardening: WebSocket upgrade handler validates `Origin` header. Local origins (no `Origin`, `vscode-webview:`, and `localhost`/`127.0.0.1`) are always allowed - note this is the **Origin-based** layer, which a non-browser client can dodge by sending none; the address-based auth gate above is what actually keeps a remote client out. Non-local origins - the private-LAN ranges (`10.x`, `192.168.x`, `172.16-31.x`) plus configured extra hosts - are gated behind the `allowNetworkAccess` config flag (default true; when false only the local machine can connect, acting as a kill switch). The Origin check is centralized in `originAllowed(origin)` (reads config fresh per call) and applied both at upgrade and, via `enforceOrigins()`, to already-open connections: `updateSettings` calls the `onSettingsChange` callback passed into `handleConnection`, which re-checks every live socket and `close(4403)`s any whose remembered Origin (tracked in a `wsOrigin` WeakMap) is no longer allowed - so turning Network access off (or removing an allowed origin) drops remote clients immediately without a server restart; localhost is never dropped. Extra hosts come from `StartServerOptions.allowedOrigins`, the `ARGUS_ALLOWED_ORIGINS` env var, and the `allowedOrigins` field in `~/.Codex/argus.json` (all three merged, comma-separated host list - e.g. the VLESS reverse-mesh entry IP - parsed into escaped `http(s)://host(:port)` regexes by `buildOriginMatcher`, read+rebuilt per-upgrade so `argus.json` edits apply without restart). `allowNetworkAccess` and `allowedOrigins` are both in `DEFAULT_CONFIG`, so the Settings UI "Network" tab can edit them via `updateSettings` - safe because `updateSettings` is only reachable over an already-authorized connection (origin + nonce both checked at upgrade). `tool_result` blocks attach to their `tool_use` by id; pure-`tool_result` user lines do not create user bubbles; user `image` blocks are preserved. `resumeSession {id}` (session.ts `handleResumeSession`) sets `s.sessionId = id` (next send spawns with `--resume`), emits `sessionLoaded {id, messages}` per-client (other clients unaffected), and then calls `channel.replaySnapshot(ws)` so any in-progress streaming indicator is restored after the reducer clears it; The modal header has a refresh icon (Feather refresh-cw) beside the close button that re-sends `listSessions` and spins (`.refreshing`) until the next `sessionList` reply lands. **List caching**: both tabs' rows are cached at module scope in `SessionHistoryModal.tsx` (`wsCache`, keyed by workspace path so a switched workspace never shows the old project's sessions, and the global `allCache`), so reopening the modal paints the previous rows instantly instead of flashing "Loading..." while the server re-reads up to 200 transcripts for the global tab. The cache is never authoritative: closing invalidates it, so every open re-requests the workspace list on mount (and the global list on its first tab visit, `loadAllOnce`) and the reply overwrites the cache. Because rows are already on screen, that fetch is a background revalidate: `refreshing`/`allRefreshing` are seeded from the cache so the wait shows on the header refresh icon instead of blanking the list. Optimistic delete and rename write through via `applySessions`, and `resume`/`resumeGlobal` call `markCurrent(id)` so the cached green highlight follows the session the user just picked rather than staying on the previously-current row. Page-scoped and never persisted (unlike the tab selection, which lives in `dialogState`). **Running marker**: a session with a turn in flight right now shows a pulsing green dot before its title in both tabs (`RunningDot`, `.runningDot`, aria-label "Working now", same green and 1.5s pulse as a pending tool call), and each row carries `data-session-id` so tests can target one session. The set comes from the server, not from the list rows: `listActiveSessions()` (channel.ts) walks every entry of every workspace channel and reports those whose `state` has a sessionId, a live `currentProc` and `cliDone === false` (`currentProc` alone is not enough, a finished turn keeps its process for reuse; `!cliDone` alone is not either, a fresh entry starts with it false and no process). `notifyActiveSessions()` pushes `activeSessions {sessions}` to every client of every channel, coalesced onto a timer (so it reads the flags after the triggering handler finished mutating them, and one turn boundary sends one message) and skipped when the set is unchanged; it fires from the entry broadcast on `thinking_start`/`done`/`error`/`sessionId`/`clear` and from entry eviction (an abandoned mid-turn entry gets its proc killed and must stop showing as running). `App.tsx` holds the ids in state (never in the row cache, which would go stale behind a closed modal) and posts `getActiveSessions` on mount and on each `ws_status connected` (the server only pushes on change, so a reconnect needs one explicit sync). Scope is this server process: a turn running under a different daemon, or a `Codex` session started outside Argus, is not marked. Security: all four validate `id` against a UUID regex and assert the resolved path stays directly inside the project dir (no traversal). - E2e tests: Playwright-based, split into two projects in `playwright.config.ts`; `mock` project matches files without `-integration` suffix, runs first with 4 workers using `window.dispatchEvent` to inject messages, no Codex CLI needed; `integration` project matches `*-integration.spec.ts` files (regex `/-integration\.spec/`), runs after mock finishes (`dependencies: ['mock']`) to avoid OOM from concurrent CLI processes + Chromium instances; naming convention: integration tests must have `-integration` suffix (e.g. `chat-integration.spec.ts`), mock tests must not; `waitForApp()` in `e2e/helpers.ts` navigates with `waitUntil: 'domcontentloaded'` and retries `page.reload()` up to 3 times if React fails to mount; Chromium launched with `--disable-gpu --disable-dev-shm-usage --no-sandbox` for reduced memory; **one flat timeout for every test**: the global `timeout: 30_000` in `playwright.config.ts` applies to both projects, mock and integration alike, with `retries: 0` on `integration` so a hang isn't paid twice (the `mock` project keeps the global `retries: 1` for transient failures); this replaced an earlier `integration`-only `timeout: 90_000` override, which was too generous - a real CLI turn normally finishes in a few seconds, so a genuine hang still cost close to 90s before being reported, and nothing passing was using that headroom (the full 112-test integration run completes in ~5 min at the flat 30s, faster than the old tiered run); a per-test `test.setTimeout(...)` override is now allowed as a rare, explicitly-commented exception for a test that provably needs more (e.g. `session-browse-during-stream-integration.spec.ts`'s three-real-CLI-turn test uses `60_000`) - this reverses the old blanket "no per-test overrides" rule, which only held because 90s never needed one. **That "a few seconds" premise has since expired and the exception is no longer rare** (2026-09-06): a *fresh* session in this workspace starts at **77,346 input tokens**, because `AGENTS.md` is 193KB (~48k tokens) and is re-read on every spawn, so a turn costs 5-20s - measured at 2.9s of CLI startup plus **17.6s to first token** for `Reply with just the single word "yes"`. Seven spec files now carry overrides, and the failures they fix all look alike and mislead the same way: a different test dies each run, never on the assertion it exists for (read the page snapshot in `error-context.md` first - in the `new-chat` case the reply already said `NO MEMORY`, so only the clock had run out), a `serial` file turns one failure into ten "did not run", and a test that blows a 60s budget inside its file can run in 12.4s alone (`startStreaming` leaves a live CLI for its neighbours to compete with). **Three different budgets can bind and raising the wrong one changes nothing**: the test timeout, an assertion cap below a turn's cost (`session-browse`'s `sendAndWait` at 20s), and a hand-rolled `Date.now() + N` deadline in the test body that no config change reaches (`log-autoscroll` at 15s, which missed by 90ms) - so grep `Date.now() +` when rebudgeting. Open decision: raise the `integration` project timeout once instead of per-spec, with the durable lever being `AGENTS.md`'s own size ([!notes/tasks/e2e-turn-cost-budgets/notes.md](!notes/tasks/e2e-turn-cost-budgets/notes.md)); `fullyParallel: true` for maximum parallelism within each project (the `integration` project uses `workers: 1` - each test drives a real Codex CLI + a Chromium instance against the one shared `:3001` backend; 2 workers causes the backend to die mid-run (resource exhaustion combined with concurrent writes to `e2e/argus.json` from parallel test workers), cascading into 40+ failures; 1 worker completes the full suite in ~7 min, actually faster than 2 workers with cascades); the integration server reads `e2e/argus.json` (via `ARGUS_CONFIG`) as its full settings config, including the webview toggles (`showLogs` etc.) the webview hydrates over `getSettings` - keep `showLogs: true` there (the `log-autoscroll-integration` test needs the panel mounted; flipping it false hangs that test waiting for `[data-testid="log-list"]`); `clickAndWaitForModal()` in file-path-links uses `toPass()` retry loop for WS roundtrip tolerance; run `yarn test:clean` manually before the suite if stale processes are suspected (test-clean.js kills orphaned Codex --print agents, stale Vite/dev servers, Playwright runners + chromium, stray test daemons; protects this session's ancestor chain and the real daemon's whole process subtree (live sessions' CLIs); flags: `--dry`, `--no-Codex`); interactive scripts (`test:e2e:ui`, `test:e2e:debug`) and `test:e2e:report` do not auto-clean. **Config guard for a reused dev server**: `webServer.reuseExistingServer: true` means a `yarn dev` the user already had running (started without `ARGUS_CONFIG`) gets adopted as the backend and then reads/writes the real `~/.Codex/argus.json` instead of `e2e/argus.json` - tests fail against settings they never set, for reasons invisible in their output. `e2e/global-setup.ts` catches this before any test runs: it hits a loopback-only `GET /health` (`src/backend/index.ts`, returns `{configPath, pid}` to `127.0.0.1`/`::1` only, 403 otherwise) and throws immediately if `configPath` doesn't match the resolved `e2e/argus.json` (case-insensitive on `win32`); a server not yet reachable is not an error (a Playwright-started server always gets the right env). **Diagnosing bulk integration failures**: many integration specs failing at once is usually one cascade, not N bugs - the signature is that they share the page state `"Disconnected, reconnecting..."` and fail in run order from some point onward, meaning the shared `:3001` backend died mid-run. Playwright's `webServer` swallows backend stdout, so debug with the server owned outside the runner (`yarn dev > /tmp/be.log 2>&1 &` then `npx playwright test --project=integration --no-deps`) and check the log for `spawn UNKNOWN` / a `handleSend` stack. The look-alike is a **dev-server handover**: `reuseExistingServer: true` also adopts the still-shutting-down server of your *own* previous `npx playwright test`, and when that one exits the rest of the run fails at `page.goto` with `ERR_CONNECTION_REFUSED` on `:5173` (Vite gone, not just the backend) while `test-clean --dry` finds nothing to kill - wait until neither port has a `LISTENING` socket before re-running. **Copy `test-results/<folder>` out before any re-run**: Playwright wipes that directory at the *start* of every run, even a single-spec one, and its `error-context.md` a11y snapshot carries the app's Debug Log (raw CLI stdout events with timestamps), which usually settles app-vs-CLI questions with no re-run at all; for a flaky test it is the only record that exists. **Writing stable integration assertions**: gate on app-owned state, not model-owned output - use the Stop button (rendered for every active turn) rather than a `[class*="toolCall"]` locator (whether the model calls a tool is its own choice, so it intermittently never appears), and branch on whether the turn is still live via `stopBtn.waitFor({ state: 'visible', timeout })` rather than `isVisible()` (an immediate check that ignores its `timeout` option, so right after a UI transition it reports `false` for a stream that *is* live and sends the test down the wrong branch); never assert on data a code path cannot produce - after a **disk replay** (`loadSession` sets only `outcome: 'success'`, no `responseTime`/token fields) there is no timer element at all, so a "stream already finished" branch must `test.skip(...)` instead of asserting token counts. **CLI memory pollution**: the CLI auto-loads `~/.Codex/projects/<encoded-cwd>/memory/` into every session it spawns, so tests asserting a reset session has *forgotten* something must generate the token per run (never hard-code it), must avoid the word "remember" in the prompt (the agent obeys by writing it to the memory file, polluting the user's real memory), and must forbid tools in the recall prompt. **Two failure shapes that both masquerade as flakiness and both mislead by passing on a re-run**: a raw `ws` client must buffer frames from construction, since a replay the server sends during the upgrade (`joinEntry` -> `replayToClient`) can share a TCP read with the handshake and be emitted before a recorder attached after `await open` exists - **and the upgrade is not the only place two frames share a read**, which is the natural misreading: any two the server writes in one tick coalesce the same way mid-session, as `getAccountUsage` does whenever the usage snapshot is warm (both sends hang off the same promise, so an already-settled `usageP` leaves phase 1 and phase 2 microtask hops apart), so the buffer must also be **consumed** rather than searched, or a two-phase reply hands phase 1 back twice and the loop waits for a third frame the handler never sends; note also that a helper's own timeout throwing its own message must sit **below** the 30s test timeout or it is dead code that *deletes* the diagnostic (`usage-indicator-integration`'s `waitForFrame` sat at 45s, so its "no `<type>` frame within" line could never fire and the failure surfaced as a bare `Test timeout of 30000ms exceeded`); and a timing assertion belongs at its real boundary - `reqAt - fetchedAt > 0` is one millisecond tighter than the invariant it tests (`>=`), and it only fails on a cold cache, so it dies on the first usage call of a suite and passes every time it is re-run alone.
